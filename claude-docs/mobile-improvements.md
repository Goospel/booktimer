# 📱 모바일 실기기 개선안 — 수집 노트

> **목적**: 사용자가 **모바일 실기기에서 BookTimer(미니앱·웹)를 실제로 쓰며** 발견한 개선안을,
> 그 자리에서 잊지 않도록 받아 적는 **수집함(inbox)**이다.
> 여기 적힌 것은 **아직 분석·설계 전의 날것**이다 — 원인·해법·우선순위는 나중에 컴퓨터에서 작업할 때 판단한다.
>
> **왜 파일인가**: 기록 전용 세션의 대화만 믿으면 세션이 사라질 때 같이 날아간다. 파일로 커밋해 두면 남는다. (2026-08-21 사용자 지시)
>
> **[plan.md](../plan.md)와의 관계** — plan.md의 `## 🩹 실사용에서 발견한 문제` 표는 **이미 손대서 원인·해결이 확정된 것**의 기록이다.
> 이 파일은 그 **앞단**이다: 여기 접수 → 작업 착수 시 분석 → 해결되면 plan.md 🩹 표로 승격하고 여기선 `✅ 완료`로 닫는다.
>
> 관련: [CLAUDE.md](../CLAUDE.md) · [plan.md](../plan.md) · [changelog](changelog.md) · [troubleshooting](troubleshooting.md)

## 상태 범례

| 상태 | 뜻 |
|---|---|
| 🆕 접수 | 적어만 뒀다. 분석 전 |

## 적는 법

- 항목마다 **`M-#` 번호**를 붙인다(부여 후 재사용·재번호 금지 — 나중에 "M-7 해줘"로 지목하기 위함).
- 제목은 `### M-# · [화면] 한 줄 요약` — 목차만 훑어도 뭐가 있는지 보이게.
- **원문은 손대지 않는다.** 사용자가 적은 표현 그대로 두고, 해석은 `이해한 바`에 따로 적는다
  (해석이 틀렸을 때 원문이 남아 있어야 되돌릴 수 있다).
- 실기기에서 본 것이므로 **기기·화면(미니앱/웹)·상황**을 알면 같이 적는다 — 재현 가능성이 절반이다.

```markdown
### M-# · [화면] 한 줄 요약

- **상태**: 🆕 접수
- **적은 날**: YYYY-MM-DD
- **화면/영역**: (미니앱 홈 / 웹 내 책장 / …)
- **원문**:
  > 사용자가 적은 그대로

- **이해한 바**: (내가 해석한 문제·기대 동작 — 틀리면 사용자가 바로잡음)
- **메모**: (재현 조건·관련 코드·연관 항목 등. 없으면 생략)
```
