# T-200 · `import.meta.url`의 `.pathname`은 Windows에서 드라이브가 두 번 붙는다 — CI가 리눅스라 「로컬만 red」로 조용히 남는다

증상: 책 추가 화면을 손보려고 `typography.test.tsx`에 테스트를 얹었더니 **내가 안 건드린 기존 2건**이 함께 실패했다. `Error: ENOENT: no such file or directory, scandir 'C:\C:\Users\kimsa\…\miniapp\src\'` — 드라이브가 두 번이다. stash로 원본만 돌려도 같은 2건이 깨져 **main이 이 PC에서 이미 red**임이 드러났다. 그 코드를 만든 클라우드 세션은 「886/886 그린」으로 보고했고 CI도 초록이었다. / 원인: `new URL('.', import.meta.url).pathname`을 디렉터리 경로로 넘겼다. file URL의 `pathname`은 **항상 `/`로 시작**해서 Windows에선 `/C:/Users/…`가 된다 — node의 경로 API는 앞의 `/`를 절대경로 루트로 읽고 현재 드라이브를 덧붙여 `C:\C:\Users\…`를 훑는다. **POSIX에선 그 값이 그대로 유효한 절대경로**라 우분투 CI는 영영 초록이고, 리눅스 컨테이너에서 도는 클라우드 세션도 같은 이유로 못 본다. 즉 이 버그는 **Windows 로컬에서만 보이는데, 그 자리에서만 red라 「내 환경이 이상한가」로 오인하기 쉽다**. / 해결: node 표준 `fileURLToPath(new URL('.', import.meta.url))`로 바꿨다(이 변환이 그 함수의 존재 이유다). 되돌아가면 다시 Windows에서만 조용히 깨지므로, **왜 `pathname`이 아닌지**를 그 자리 주석에 박았다. / 재발방지: ① file URL에서 경로를 얻을 땐 **언제나 `fileURLToPath`**. `.pathname`을 fs 함수에 넘기지 않는다 — 리뷰에서 볼 곳은 「URL을 문자열 경로로 쓰는 자리」다. ② **「CI 초록」은 「리눅스에서 초록」이라는 뜻이다.** 개발은 Windows인데 CI·클라우드 세션은 리눅스인 이 레포에선 경로·인코딩·개행처럼 OS가 갈리는 자리에서 **양쪽 신호가 구조적으로 어긋난다**. 다른 세션이 그린을 보고했어도 **손대기 전 로컬에서 한 번 돌려** 기준선을 확인한다 — 안 그러면 남의 red를 내 변경 탓으로 오진하거나, 반대로 내 red를 「원래 그런가 보다」로 넘긴다. 1회차 신규
