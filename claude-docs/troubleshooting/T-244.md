# T-244 · 워크트리 `node_modules` 정션이 가리키는 main 폴더에 옛 SDK가 남아, lock이 올라가도 미니앱 번들이 옛 SDK로 조용히 빌드될 뻔했다 — `deploy.sh`의 산출물 검사는 이걸 못 가른다

**2회차(T-150 「옛 입력으로 빌드」 군)** / 증상: 번들 `20260913-148`(SDK 3.0.4) 검수가 반려도 승인도 없이 16시간째 PENDING이었다(직전 검수들은 12~16분). 사용자 경험칙 「이럴 땐 SDK가 구버전인지 보고 올려서 재요청하면 금방 된다」로 확인해 보니 콘솔 공지 53009(「3.0.0~3.1.0은 Origin이 달라 최신으로 업데이트」)·52453(「9월 14일까지 SDK 3.x 전환」)이 있었고, lock은 dependabot #976(2026-09-13 23:17 KST 머지)으로 이미 `^3.1.1`이었다. 그런데 이 워크트리의 `miniapp/node_modules`는 main 폴더로 가는 정션이고 거기 설치본은 **3.0.4**였다 — 그대로 `deploy.sh`를 돌렸으면 `-149`도 3.0.4로 나갔다. ⚠️ `-148` 자체는 #976 머지 **전**(20:38 KST 업로드)이라 당시 lock과 일치했다 — 어긋남은 lock 갱신 뒤 설치가 따라가지 않은 틈이다(세션 중 한때 「-148도 lock과 다르게 빌드됐다」고 잘못 보고했다). / 원인: SessionStart 훅이 모든 워크트리의 `node_modules`를 main 폴더 하나로 정션한다. dependabot은 PR로 lock만 바꾸고, main 폴더는 다른 세션의 브랜치라 아무도 `npm ci`를 다시 돌리지 않는다. `npm run build`는 lock이 아니라 **설치된 것**으로 빌드하고, `deploy.sh`의 검사(마커·localhost·목 코드·.ait 해시)는 전부 산출물 내용이라 SDK 버전이 달라도 그대로 통과한다. 콘솔 `bundle_list`의 `sdkVersion`은 **업로드 뒤에야** 보인다. / 해결: 이 워크트리 정션만 끊고(`cmd /c rmdir`, main 항목 수 154→154 확인) `npm ci` → 3.1.1 · `tsc -b` 0 · vitest 1561 통과 → 운영 CORS 프리플라이트(`apps`·`private-apps` 오리진 200) → `-149` 업로드(콘솔 `sdkVersion` 3.1.1) → 사용자 동의로 `-148` 검수 취소 → `-149` 검수 요청. / 재발방지: `deploy.sh` ⓪ — 빌드 **전에** 직접 의존성(`dependencies`+`devDependencies`)의 설치본을 lock 버전과 대조해 다르면 패키지별 「설치 X ≠ lock Y」와 정션 끊기+`npm ci` 안내로 차단. 스모크 Case 8(Red 4건 → Green) · 돌연변이(`if bad:`→`if False:`) 사살 · 실제 배치 음성 대조군(이 lock + main 정션 → `@apps-in-toss/web-framework 3.0.4≠3.1.1`·`vitest 4.1.10≠4.1.11`로 차단). ⚠️ **다른 워크트리들은 여전히 main의 옛 설치본을 가리키므로 거기서 배포하면 이 가드에 걸린다** — 의도한 동작이다. ⚠️ **CORS**: 라이브 `-147`은 SDK 3.0.4라 옛 오리진(`web`·`private-web`.tossmini.com)을 쓴다 — 3.1.1+ 번들이 라이브가 되기 전엔 SSM `MINIAPP_ALLOWED_ORIGINS`에서 옛 오리진을 지우면 안 된다. / 사용자 경험칙(검수 정체 → SDK 버전 확인 후 재요청)의 효과는 이 항목 작성 시점 `-149` 검수 결과 미확인 — 공지 52775의 「9월 14일부터 수정 검수 요청 집중」도 정체의 다른 설명일 수 있다. / **관련**: T-150(같은 군 1회차 — 빌드 무성 no-op) · T-110(같은 정션의 삭제 사고) · 글로벌 「통과는 증거가 아니다」(배포 게이트 통과 ≠ lock대로 빌드).
