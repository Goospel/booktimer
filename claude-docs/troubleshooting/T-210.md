# T-210 · 한 브랜치가 changelog의 자기 행을 「추가 → 수정」하면 rebase가 그 행을 중복 생성한다 — `merge=union`이 시키는 대로 한 결과라 충돌도 테스트 실패도 없다

**3회차(#940·#944·#1038 — 앞의 둘은 같은 세션 안에서)** / 증상: 리뷰 반영이 있던 PR 둘이 **둘 다** rebase 뒤 changelog에 같은 날짜·같은 제목 행을 두 개 남겼다. 초판과 최종본이 나란히 서 있는데 rebase는 「Successfully rebased」라 말하고, 미니앱 1067건도 전부 그린이다 — 내가 눈으로 세지 않았으면 **중복 행이 그대로 main에 갔다.** / 원인: `.gitattributes`의 `claude-docs/changelog.md merge=union`(T-098 하드픽스)이다. union은 양쪽 새 행을 마커 없이 **둘 다** 남기는데, 그건 「두 세션이 각자 맨 아래에 행을 붙인다」는 원래 시나리오에선 정답이다. 그런데 **한 브랜치가 자기 행을 두 커밋에 걸쳐 「추가 → 수정」**하면(기능 커밋에서 행 추가, 리뷰 반영 커밋에서 그 행 보강 — 이 레포의 표준 흐름이다) rebase가 커밋을 하나씩 재적용하면서 **커밋1의 초판과 커밋2의 최종본을 서로 다른 행으로 보고 둘 다 남긴다.** 즉 우연이 아니라 **구조적**이라, 그 패턴이면 매번 난다. / 해결: 최종본만 남기고 초판 행을 지운 뒤 재커밋. **하드픽스로 승격했다** — `require-changelog-no-dup.ps1`(PreToolUse, `git push` 게이트)이 changelog에서 「같은 날짜 + 같은 굵은 제목」 행이 둘 이상이면 차단한다. 본문은 키에 넣지 않는다 — 넣으면 초판과 최종본이 다른 행으로 보여 아무것도 못 잡는다. 우회는 `ALLOW_CHANGELOG_DUP`. 테스트 8건(`tests/test-require-changelog-no-dup.sh` — 차단·정상·같은날 다른제목·commit 미개입·override·fail-open·**비인접 중복**까지. 마지막 건이 「이웃끼리만 비교하는」 구현을 배제한다). / 재발방지: ① 훅이 1차 방어다. ② 손으로 막으려면 rebase 직후 `git diff origin/main -- claude-docs/changelog.md`로 **자기 행이 정확히 1줄인지** 확인한다. ③ 더 근본적으로는 changelog 한 줄을 **브랜치의 마지막 커밋 하나**에만 두면 「추가 → 수정」 구조 자체가 안 생긴다. ④ ⚠️ **훅은 PowerShell이라 원격(웹) 세션엔 안 붙는다**(T-208의 교훈) — 그 환경에선 ②를 손으로 밟는다. ⑤ **초판 행을 지울 땐 본문 어구가 아니라 굵은 제목으로 앵커를 잡는다** — 3회차에서 본문 어구(「돌연변이 N종 사살」)로 지우려다 **다른 changelog 행 4개가 같이 걸려** 스크립트가 자기 가드에 멈췄다. 본문 어구는 이 레포에서 재사용되는 정형구라 유일하지 않다. ⑥ **②의 검사 기준은 시점에 따라 다르다(4회차 #1099, 2026-09-11)** — 브랜치가 origin/main보다 **BEHIND인 동안** `git diff origin/main -- changelog.md`는 main에 새로 들어온 남의 행을 **내 삭제(`-`)처럼** 보여 준다(`1 1`). 4회차에서 이걸 「내 행 유실」로 오판할 뻔했다. 리베이스 **전**엔 `git diff $(git merge-base HEAD origin/main) -- changelog.md`(merge-base 기준)로 내 추가 행만 세고, 리베이스 **후**에 `origin/main` 기준으로 중복을 본다. 4회차도 훅이 아니라 이 수동 확인이 잡았다 — 하드픽스는 여전히 실전 미발화. ⑦ **5·6회차(#1113·#1115, 2026-09-13) — 정리 커밋으로 지운 초판 행이 다음 rebase에서 되살아난다.** 같은 세션의 병렬 PR 둘(웹·미니앱)에서 또 났고, #1115는 한 단계 더 나빴다: 초판 행을 지우는 정리 커밋을 올린 뒤 #1120이 머지돼 다시 rebase하자 **초판 행이 돌아왔다.** union은 충돌 구간에서 양쪽 줄을 다 남기므로, **내 행을 고치거나 지우는 커밋이 main 끝에 새로 붙은 남의 행과 이웃하면 수정·삭제를 표현하지 못한다.** 정리 커밋은 적용 결과가 무변경이 되고, git은 그 커밋을 `dropping <sha> ... -- patch contents already upstream`이라며 **조용히 버린다**(「이미 반영됐다」로 읽혀 더 헷갈린다). 스크래치 레포로 재현했다: 추가→수정 2커밋 rebase = 2행 → 정리 커밋 후 main에 행 추가 + 재rebase = 정리 커밋 drop·2행 복귀 → `git reset --soft $(git merge-base HEAD origin/main)`로 한 커밋에 합친 뒤 rebase = 1행. **처방: 리뷰 반영으로 자기 행을 두 번 건드린 브랜치는 정리 커밋을 쌓지 말고 한 커밋으로 합친 뒤 rebase한다**(squash 머지라 최종 결과는 같다 — ③을 사후에 적용하는 것). 이번에도 훅은 안 울렸는데 **이번엔 원리상 못 울렸다** — push를 `cd <다른 워크트리> && git push`로 해서 훅이 세션 cwd의 changelog를 봤다(T-242, 하드픽스 #1118 진행 중). 그러니 「훅 미발화」 연속 기록 중 5·6회차는 훅의 효력에 대해 아무것도 말하지 않는다. ⚠️ **7회차(#1124, 2026-09-13) — 6회차 변종의 실전 재현, 한 브랜치에서 세 번.** ① 구현자의 리뷰 반영 rebase에서 2행 → 수동 dedup. ② `pr-merge.sh`가 DIRTY를 보고해 코디네이터가 다시 rebase → 또 2행 → **정리 커밋을 쌓아** 지우고 push. ③ CI 도는 사이 main이 #1123으로 전진해 다시 rebase → git이 그 정리 커밋을 `dropping … patch contents already upstream`으로 버리고 **초판 행이 돌아왔다** — 6회차가 스크래치로 재현한 명제가 실전에서 문자 그대로 났다. 처방은 6회차 그대로: `git reset --soft origin/main`으로 기능·리뷰·정리 3커밋을 1커밋으로 합쳐 push → 그 뒤 재발 0. **배운 것 둘**: ⓐ 6회차 처방이 트래커·CLAUDE.md에 적혀 있었는데도 ②에서 정리 커밋을 쌓았다 — 「rebase 뒤 2행」을 본 순간의 반사가 「지우기」라서, prose는 이 반사를 못 바꿨다 → **하드픽스 2단으로 승격**: rebase 직전 게이트 `require-single-changelog-commit-before-rebase.ps1`(`merge-base..HEAD`에서 changelog를 건드린 커밋이 2개 이상이면 차단 + `git reset --soft <base>` 안내, 우회 `ALLOW_MULTI_CHANGELOG_REBASE`). ⓑ 훅은 이번에도 안 울렸다 — 세션 cwd에서 push했으니 T-242 사각은 아니고, **push 전 수동 확인이 매번 먼저 잡아 훅이 볼 중복이 남아 있지 않았다**(7회 연속 미시험). / **관련**: T-098(changelog merge=union 도입 — 이 함정의 원천이자 여전히 옳은 하드픽스) · T-208(승격 산출물이 특정 도구에 묶이면 그 도구가 없는 환경에서 방어가 0이 된다)
