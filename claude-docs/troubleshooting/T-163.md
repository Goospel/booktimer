# T-163 · 목 모드는 「SDK가 첫 관문인 기능」의 성공 경로를 원리상 검증하지 못한다 — 목 라우트를 깔아도 도달 자체가 불가능하다

증상: 미니앱 회원 탈퇴 설계가 수동 검증 게이트로 "목 모드에서 탈퇴 플로 → 로그인 브릿지 복귀를 눈으로 확인"을 요구했는데, 구현 단계에서 **실행 자체가 불가능**했다. 탈퇴 버튼을 누르면 `tossLogin()`이 "apps-in-toss 웹뷰 환경이 아니에요"로 즉시 떨어져 그 뒤(서버 호출·삭제·복귀)로 한 발도 못 간다. 서버 API에 목 라우트를 깔아 둬도 소용없다 — 막히는 지점이 **네트워크 앞단**이기 때문이다. / 원인: 이 기능의 **확인 수단이 토스 SDK 자체**다(탈퇴는 fresh 인가코드로 본인을 재확인한다). 목 모드는 `api.ts`가 서버 응답을 대신 돌려주는 구조라 **HTTP 경계 뒤쪽만** 대역할 수 있고, SDK 호출은 그 경계 앞에 있다. 즉 「목에 라우트가 있는가」와 「목으로 그 플로를 탈 수 있는가」는 다른 질문인데, 설계가 전자만 보고 후자를 낙관했다. 같은 구조가 광고(리워드)·푸시 알림 동의에도 그대로 있다 — SDK가 관문인 기능 전부. / 해결: **목 우회를 심지 않았다.** `toss.ts`에 DEV 분기를 넣으면 브라우저에서는 통과하지만 **확인 수단의 코드 경로가 약해진다** — 되돌릴 수 없는 파괴적 기능에서 그 대가는 너무 크다. 대신 ① 목으로 도달 가능한 구간(시트 개폐·경고 문구·취소·에러 표시·링크 이동)만 게이트로 두고 ② 성공 경로는 **실기기 확인 항목**으로 분리해 명시했다. 실패가 시트를 닫지 않고 안에 표시되는 것은 목으로 확인된다. / 재발방지: ① **설계에서 수동 검증 게이트를 적을 때 「이 플로의 첫 관문이 SDK인가」를 먼저 묻는다** — 그렇다면 목 게이트를 적지 말고 처음부터 실기기 항목으로 쓴다(구현자가 실행 불가능한 게이트를 받아 시간을 태우지 않게). ② 목 우회로 SDK 게이트를 뚫는 유혹을 경계한다 — 특히 **인증·결제·삭제처럼 그 SDK 호출이 곧 보안 경계인 경우 금지**. ③ 목의 대역 범위를 한 줄로 기억한다: **`api.ts`의 HTTP 경계 뒤쪽만**. 큰 결로는 T-149·T-161(계측기가 그 실패를 볼 수 없다)·T-150(배포 전 확인이 비변별)과 닿지만, 저쪽들은 **계측기가 통과시켜 거짓 안심**을 주는 반면 이쪽은 **계측기가 아예 실행되지 않아 즉시 드러난다**(그래서 사고로는 안 이어졌고 설계 낭비만 남았다) — 메커니즘이 반대라 1회차 신규로 등재하고 재발·승격 트래커엔 올리지 않는다. 같은 「SDK가 관문이라 목으로 못 감」이 2회째 나오면 그때 군을 만든다. 미니앱 회원 탈퇴 구현 중 발생
