# T-167 · 리버스프록시가 `Forwarded`(RFC 7239)를 안 지우면 클라이언트가 자기 IP를 신고할 수 있다 — `X-Forwarded-For`만 막혀 있다고 안심하면 놓친다

증상: 겉으로는 아무 증상이 없다. `LoginAttemptService`의 IP별 5회 잠금은 테스트도 통과하고(`LoginBruteForceTest`가 `setRemoteAddr`로 IP를 직접 주입한다) 운영 로그도 정상이다. 그런데 `POST /login`에 `Forwarded: for=203.0.113.<n>`을 매번 바꿔 붙이면 카운터가 영원히 1에 머물러 **잠금이 100% 우회**된다. 앞단에 WAF·레이트리밋이 없어 이게 온라인 비밀번호 추측의 유일한 통제다. / 원인: 두 사실이 곱해진다. ① 앱이 `WebConfig`에서 `ForwardedHeaderFilter`를 `HIGHEST_PRECEDENCE`로 등록한다(OAuth redirect_uri·쿠키 secure 때문에 필요하다) → 보안 필터보다 먼저 요청을 감싸 `getRemoteAddr()`가 헤더 기반 값을 돌려준다. ② **Spring은 `Forwarded`를 `X-Forwarded-*`보다 우선**하는데, Caddy는 이 헤더를 세팅하지도 삭제하지도 않아 클라이언트 값이 그대로 통과한다. ⚠️ **최초 진단은 틀렸다** — 코드리뷰 에이전트는 「Caddy가 XFF에 append하므로 최좌측=공격자 값」이라고 결론냈지만, 도커 프로브 실측(caddy v2.11.4)에서 스푸핑한 `X-Forwarded-For: 203.0.113.9`는 **버려지고** 실제 peer IP로 리셋됐다 (Caddy 2.7+는 `trusted_proxies` 미설정이면 들어온 XFF를 신뢰하지 않는다). 같은 요청에서 `Forwarded`만 그대로 도달했다. 즉 **잡은 결론은 맞고 메커니즘은 틀린** 사례다. / 해결: `deploy/Caddyfile`의 `reverse_proxy` 블록에 `header_up -Forwarded` 한 줄. Caddy가 절대 만들지 않는 헤더이므로 입구에서 통째로 버리는 게 정답이다(스킴·호스트까지 실려 OAuth redirect_uri도 함께 오염된다). **곁들여 발견한 더 큰 결함**: Caddyfile 변경에는 **배포 반영 경로가 없었다** — 워크플로가 `deploy/`를 S3로 내려주지만 Caddy는 마운트된 파일을 다시 읽지 않고, `deploy-on-ec2.sh`는 주석대로 의도적으로 Caddy를 안 건드렸다. 앱 전환 앞에 `caddy reload`를 치는 2.5단계를 넣었다(무중단 실측: reload 2회 × 부하 400건, 실패 0건). / 재발방지: ① **「프록시가 무엇을 덮어쓰는가」는 문서가 아니라 실측으로 확인한다** — 프록시별·버전별로 다르고(append/replace/무시), 떠다니는 태그(`caddy:2-alpine`)면 언제든 바뀐다. 컨테이너 2개(에코 업스트림 + 프록시)와 스푸핑 클라이언트면 2분이면 잰다. ② **`X-Forwarded-For`를 막았다고 신원 위조를 막은 게 아니다** — 같은 정보를 나르는 헤더가 최소 둘(`Forwarded` 포함)이고 프레임워크마다 우선순위가 다르다. 프레임워크가 **실제로 읽는 순서**를 확인해라(Spring = `Forwarded` 우선). ③ **`getRemoteAddr()`를 보안 결정(잠금·레이트리밋)의 키로 쓰는 코드는 그 값의 출처를 반드시 따라가라** — `ForwardedHeaderFilter`가 끼어 있으면 그건 더 이상 peer IP가 아니다. ④ 이 클래스는 **앱 테스트로 원리상 못 잡는다**(경계가 프록시에 있고, MockMvc는 `setRemoteAddr`로 결과를 직접 정한다). 실 Caddy 컨테이너 회귀 테스트 `deploy/tests/test-caddy-forwarded.sh`를 **CI에 배선**했다 — 안 돌아가는 가드는 가드가 아니다. ⑤ 인프라 설정 변경은 「머지되면 반영되는가」를 코드와 별개로 확인해라 — 이번엔 반영 경로 자체가 없어 수정이 무의미할 뻔했다. 1회차 신규. 전체 코드리뷰(좀비·보안 2축, 47-에이전트 워크플로) 후속 수정 중 실측으로 확정

- **2회차** (2026-08-15): **2회차 — 「reload를 추가했다」로 끝난 게 아니었다. 파일 하나를 bind mount 하면 배포가 그 파일을 바꿔도 컨테이너는 영원히 옛 내용을 본다** / 증상: `header_up -Forwarded`를 넣고 머지·배포까지 전부 초록이었다 — CI 통과, EC2 로그에 `[deploy] Caddyfile 반영 (caddy reload)` 출력, `caddy reload` exit 0, 라이브 헬스체크 통과. 그런데 운영에 스푸핑 요청을 넣으니 **그대로 뚫렸다**: `curl -H 'Forwarded: for=203.0.113.9;host=evil.example;proto=http' https://booktimer.app/settings` → `Location: http://evil.example/login`(헤더 없이 보내면 `https://booktimer.app/login`). 어느 단계도 실패 신호를 내지 않아, 배포 로그만 보면 반영됐다고 판단하게 된다. / 원인: `compose.prod.yaml`이 **파일 하나**를 마운트했다(`./Caddyfile:/etc/caddy/Caddyfile:ro`). 리눅스에서 파일 bind mount는 **컨테이너 기동 시점의 inode에 고정**되는데, 배포의 `aws s3 sync`는 임시파일을 받아 **rename으로 교체**한다(새 inode) → 컨테이너는 옛 inode를 계속 본다. 그래서 `caddy reload --config /etc/caddy/Caddyfile`은 **낡은 내용을 다시 읽고 정상 성공**한다(유효한 설정이니 exit 0). 즉 caddy 컨테이너가 마지막으로 뜬 이후의 **모든 Caddyfile 수정이 조용히 무효**였다. ⚠️ **로컬(Windows Docker Desktop) 재현으로는 판정할 수 없다** — Windows 공유 계층(virtiofs)은 rename을 반영해 `NEW`가 보인다. VM 내부 경로(`/var/tmp/...`)로 마운트해야 리눅스 네이티브 의미론이 나오고, 그때 비로소 `OLD`가 재현된다(둘 다 실측). / 해결: **디렉터리를 마운트한다** — `deploy/caddy/Caddyfile` + `./caddy:/etc/caddy:ro`(디렉터리 마운트는 내부 rename을 정상 반영, 실측). 배포는 3단계로: ① 운영과 **동일한 마운트**로 일회용 컨테이너에 `caddy validate`(문법 오류·마운트 경로 오타를 라이브를 건드리기 전에 잡는다 — 유일한 입구라 잘못 뜨면 전면 장애) → ② `dc up -d caddy`(서비스 **정의**가 바뀐 경우에만 재생성하므로 평시 배포엔 no-op = 순단 0) → ③ `caddy reload` **재시도 루프**(방금 재생성됐으면 admin API :2019가 아직 안 떠 첫 시도가 실패할 수 있고, 그대로 두면 `set -e`가 배포를 죽인다). / 재발방지: ① **「배포가 성공했다」와 「변경이 적용됐다」는 별개 명제다** — 특히 프록시·설정 파일은 배포 로그가 아니라 **바깥에서 관측 가능한 동작**으로 확인해라. 이번엔 `curl` 한 줄(스푸핑 헤더 → `Location` 관찰)이 유일하게 진실을 말했다. ② **단일 파일 bind mount는 안티패턴이다** — 설정 파일을 컨테이너에 넣을 땐 디렉터리째 마운트한다. 파일 마운트는 「호스트에서 고치면 반영된다」가 **제자리 수정(`>>`, `sed -i` 없는 편집)일 때만** 참이고, rename으로 교체하는 도구(`aws s3 sync`·`mv`·대부분의 에디터·`sed -i`)엔 거짓이다. ③ 회귀 가드를 compose에 걸었다 — `test-caddy-forwarded.sh`가 마운트가 디렉터리인지 단언한다(파일 마운트로 되돌리면 실패). 프록시 동작 단언 5개가 전부 통과해도 이 하나가 깨지면 운영엔 무반영이라, **같은 테스트 안에 둔 것**이 요점이다. ④ 교훈의 일반형: **플랫폼 의미론(리눅스 vs Docker Desktop)이 갈리는 것을 로컬 재현으로 판정하지 마라.** 재현 환경이 운영과 같은 커널 경로인지 먼저 확인한다. 2회차(T-167 1회차 = `Forwarded` 미삭제). 1차 수정이 운영에서 무효임을 배포 직후 실측으로 확인해 등재
