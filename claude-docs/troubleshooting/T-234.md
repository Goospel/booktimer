# T-234 · 콘솔 MCP `miniapp_update_screenshots`는 성공해도 `{"miniAppId":…,"appName":null}`만 돌려주고, 직후 `miniapp_get`·`miniapp_meta_status`는 옛값을 보여 「안 됐다」로 읽힌다 — 재호출하면 앱정보 검토가 두 번 접수될 수 있다**) / **1회차

증상: 홈 피드 「여백」 탭 출시 전 스토어 컷 `02-feed`를 새 그림으로 바꾸려 `image_upload_url` → PUT(200, 공개 URL 695,952B 확인) → `miniapp_update_screenshots`를 불렀다. 응답은 `{"miniAppId":61047,"appName":null}`뿐이었고, 바로 이어 부른 `miniapp_get`은 `displayOrder 1`에 **옛 URL**, `miniapp_meta_status`는 `reviewState=APPROVED · isEditable=true`였다. 실패로 판단해 같은 페이로드로 **한 번 더** 불렀고, 그 뒤 조회에서야 새 URL + `IN_REVIEW · isEditable=false`가 나왔다. / 원인: 두 가지 중 어느 쪽인지 **가르지 못했다** — ① 첫 호출이 실제로 접수됐고 조회 반영만 늦었다(그러면 두 번째 호출은 중복 접수) ② 첫 호출이 조용히 실패했다. 응답 본문이 결과를 말해 주지 않고(`appName:null`은 성공·실패 양쪽에서 같은 모양일 수 있다), 조회 API의 반영 시차도 문서에 없다. 검토 승인은 몇 시간 뒤 정상으로 났고 새 그림이 콘솔에 실렸다 — 즉 최종 결과는 옳았지만 **판정 근거가 없는 재호출**이었다. / 해결: 결과는 `miniapp_meta_status`의 `reviewState`가 `IN_REVIEW`로 바뀌는 것으로 판정한다(응답 본문이 아니라). 바뀔 때까지 **수십 초 간격으로 몇 번 재조회**한 뒤에도 그대로면 그때 재호출한다. / 재발방지: ① 콘솔 MCP의 「쓰기」 tool은 응답 본문을 성공 증거로 삼지 않는다 — 상태 조회 tool로 상태 전이를 확인한다(같은 규칙이 `bundle_submit_review` → `reviewStatus=REVIEWING`, `bundle_test_push` → `isTested=true`에 이미 적용돼 있었다). ② 즉시 재조회의 「옛값」은 실패 증거가 아니다 — 글로벌 「통과는 증거가 아니다」의 반대 방향(실패도 증거가 아니다)이다. ③ 재호출은 중복 접수 비용이 있으니 대기 → 재조회 → 그래도 옛값 → 재호출 순으로
