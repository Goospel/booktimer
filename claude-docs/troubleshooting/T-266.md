# T-266 · Git Bash의 openssl base64 출력은 CRLF로 끝난다 — 비밀값 끝에 `\r`이 남는다

## 증상

- 설계서의 생성 명령 `printf 'booktimer:%s' "$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=\n')" > F`을 그대로 돌렸다.
- `wc -c < F`가 기대한 53(`booktimer:` 10 + base64url 43)이 아니라 **54**였다.
- 마지막 바이트를 `tail -c 1 F | od -An -tx1`로 보니 `0d`였다. `\r` 1개, `\n` 0개.
- `aws ssm put-parameter --value file://F`는 그대로 성공했다(버전 1). 어느 도구도 경고하지 않았다.

## 원인

- 이 머신(Windows 11 · Git Bash)의 `openssl rand -base64` 출력 줄 끝이 `\r\n`이었다. `$(…)`는 끝의 `\n`만 떼고 `\r`은 남긴다.
- `tr -d '=\n'`은 `\n`만 지운다. 그래서 `\r` 한 글자가 값 끝에 붙은 채 파일과 SSM에 들어갔다.
- 사람이 메모장에서 복사할 때 `\r`이 따라가는지 아닌지에 따라 콘솔 값과 서버 값이 갈린다. 둘 다 「맞는 값」처럼 보여서 눈으로는 못 가린다.

## 해결

- `tr -d '=\r\n'`으로 다시 만들었다 → 53바이트 · `\r` 0 · `\n` 0 · 허용 문자(`A-Za-z0-9_-`) 밖 0.
- `put-parameter --overwrite`로 바꿨다(버전 2). 파일과 SSM 복호값(`--with-decryption … | tr -d '\r\n' | sha256sum`)의 sha256이 일치했다.
- 아직 아무 데도 쓰이지 않은 값이라 교체 비용이 없었다(운영 서버는 배포 때 SSM을 읽는다).

## 재발 방지

- Windows 네이티브 도구의 출력을 `$(…)`로 받아 값으로 쓸 때는 `\r`부터 의심한다. 지우는 쪽은 `tr -d '\r\n'`처럼 둘 다 적는다.
- 비밀값처럼 **눈으로 보면 안 되는 값**은 바이트로만 판정한다 — 길이 · CR 수 · 끝 바이트 · 허용 문자 밖 개수. 「길이가 기대와 다르다」 하나로도 충분히 잡힌다(이번에 잡은 신호).
- 넣은 뒤엔 저장소 값과 원본 파일의 해시를 대조한다. 성공 응답(버전 번호)은 값이 맞다는 증거가 아니다.
