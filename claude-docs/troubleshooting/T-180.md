# T-180 · 목 모드는 `fetch`를 아예 안 태운다 — 「요청이 몇 건 나가나」를 네트워크 탭으로 세면 항상 0건이라 그 게이트는 원리상 공허하다

증상: 서재 인라인 여백 박스의 debounce가 캐러셀 훑기 요청을 실제로 누르는지 확인하려고 playwright `page.on('request')`로 `/api/stories/of/` 요청을 셌다. 결과는 **0건** — 통과처럼 보인다. 그런데 같은 화면에서 박스는 분명히 글을 받아 그리고 있었다(0건인데 데이터가 있다). 계수기가 0을 돌려준 이유가 「debounce가 완벽하다」인지 「애초에 셀 것이 없다」인지 구분할 수 없고, **debounce를 통째로 지워도 0건은 그대로**라 이 게이트는 무엇도 증명하지 못한다. / 원인: `api.ts`의 `request()`가 첫 줄에서 `if (DEV_MOCK) return (await import('./dev-mock')).mockRequest(...)`로 갈라진다 — 목 모드에서는 HTTP 요청이 **한 번도 만들어지지 않는다**(그래서 서버·토큰 없이 전 화면이 뜨는 것이고, 그게 목 모드의 설계 의도다). 네트워크 탭은 실제 요청만 보므로 원리상 0이다. 함정의 핵심은 **0이 「좋은 결과」의 모양을 하고 있다**는 것 — 「요청이 안 나갔다」가 곧 기대값이라 계측기가 죽은 것을 성공으로 읽게 된다. / 해결: 계측 지점을 **목 경계**로 옮겼다 — `dev-mock.ts`의 `mockRequest` 진입부에 임시 계수기(`window.__calls.push(method + path)`)를 심고 훑기 전후로 세서 「3권을 훑는 동안 0건, 정착한 책만 1건」을 실측한 뒤 계수기를 제거했다. 임시 계측 코드는 게이트 직후 되돌리고 `git diff --numstat`으로 잔재 0을 확인한다. / 재발방지: ① **계측기를 붙이기 전에 「이 값이 0이 아닐 수 있는가」를 먼저 확인한다** — 셀 수 없는 자리에 계수기를 놓으면 0이 나오고, 0은 대개 기대값이라 통과로 읽힌다(공허한 단언의 브라우저 판). ② **목·스텁이 실경로를 우회하는 계층을 넘어서 계측하지 않는다** — 목 모드에서 재는 것은 fetch·XHR·네트워크 타이밍이 아니라 **목이 받은 호출**이다. ③ 이번처럼 계측을 위해 소스를 임시로 고쳤으면 **되돌림을 diff로 확인**한다(`myHandle=null` 스위치와 같은 취급). ④ 판별 질문 하나면 된다: **「내가 겨눈 로직을 지웠을 때 이 계측기가 다른 값을 내는가」** — 그 답이 «아니오»면 게이트가 아니라 장식이다. **5회차 = T-144·T-145·T-149·T-161 재발군**(통과가 증거가 아닌 상태 — 앞 넷은 단위 테스트의 하니스·매처였고, 이번엔 **브라우저 게이트의 계측 지점**이라 축이 하나 늘었다) — 트래커 갱신
