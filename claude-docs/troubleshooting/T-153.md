# T-153 · `deploy.sh --expect`에 코드 조각을 주면 minify가 변형해 검증이 헛돈다 — 마커는 압축 불변 문자열 리터럴이어야 한다

증상: 잔디 방향 핫픽스 배포에서 `--expect "slice(0,15)"`로 걸었더니 클린 빌드가 성공했는데도 "번들에 없다"로 배포가 차단됐다 — 소스엔 그 코드가 분명 들어 있다. / 원인: vite minify가 숫자 상수를 호이스팅·개명해 `slice(0,15)`가 번들에서 `slice(0,EGe)` 형태로 변형됐다. `--expect`는 dist 산출물을 그대로 검색하므로 식별자·숫자 인자·공백을 포함한 **코드 조각은 압축 후 형태가 보존되지 않아** 소스 기준 문자열과 어긋난다. / 해결: dist를 직접 열어 변형된 실제 형태를 확인한 뒤, 압축이 건드리지 않는 마커(사용자 노출 한글 UI 문구)로 바꿔 재배포. / 재발방지: `--expect` 마커는 **문자열 리터럴(한글 UI 문구)**로 고른다 — minify는 문자열 리터럴의 내용은 변형하지 않는다. 코드 조각은 금지. CLAUDE.md 「미니앱 개발 루프」 절에 한 줄 승격 기재. 1회차 신규 — "검증기가 신호를 못 보는" 결이 T-150(비변별 마커)과 닿지만 방향이 반대다(저쪽은 어느 번들에나 있어 통과, 이쪽은 새 번들에 있는데 실패). 미니앱 잔디 핫픽스 배포 중 발생) **· 보강 2026-08-14(2회차, 다른 변형)**: 이번엔 코드 조각이 아니라 **런타임에 조립되는 문자열**을 마커로 줘서 같은 자리에서 막혔다 — 서재 메타 두 줄 배포에 `--expect "11시간"`을 걸었는데, 그 값은 `formatDuration(seconds)`가 **실행 중에 만들어 내는 것**이라 번들엔 리터럴로 존재하지 않는다(있는 건 `시간`·`분` 같은 조각과 조립 코드뿐). 즉 마커의 자격은 「문자열 리터럴인가」가 아니라 **「소스에 리터럴로 적혀 있어 번들에 그대로 실리는가」**다 — 포맷 결과·템플릿 보간 결과·i18n 키로 조회한 값은 전부 실격. 판별법: **그 문구를 소스에서 따옴표째 찾을 수 있어야 한다**(`formatDuration(...)`처럼 함수가 만들면 실격). ⚠️ 이번 확인 중 곁가지 함정 하나 더 — `Get-Content -Raw`(PowerShell 5.1 기본 ANSI/CP949)로 번들을 읽으면 **한글이 깨져 `.Contains('저자 미상')`이 거짓**이 된다. 하마터면 "minify가 한글을 이스케이프한다"는 엉뚱한 결론으로 갈 뻔했다 — 번들의 한글을 검사할 땐 반드시 `-Encoding UTF8`(글로벌 「Windows 셸 원칙」 2번의 읽기 방향 변형). 이번 릴리스처럼 **새 UI 문구가 0인 변경**(순수 동작·레이아웃 수정)은 애초에 자격 있는 마커가 없으므로, 마커를 억지로 만들지 말고 `--expect` 없이 클린 빌드 + `.ait` 바이트 해시 검증에 맡긴다.
