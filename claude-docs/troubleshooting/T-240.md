# T-240 · 대기 루프의 종료 조건에 성공만 넣으면 실패에 침묵한다 — 그리고 그 침묵은 「아직 진행 중」과 구별되지 않는다

**1회차(두 사례가 같은 날 나왔다)** / 증상: 같은 세션에서 두 번. ① **서버 기동 대기** — `until curl … ; do if ! pgrep -f GradleWrapperMain; then echo 실패; fi; sleep 3; done`으로 「떴거나 죽었거나」를 잡으려 했는데, **이 환경(Git Bash)에 `pgrep`이 없어서**(`command not found`) 프로세스 검사가 **항상 참**이 됐다. 서버는 MySQL 이미지를 받으며 멀쩡히 올라오는 중이었는데 루프가 「기동 실패」를 외치고 죽었다 — **가짜 실패**. ② **PR 머지 대기** — `until [ state = MERGED ]; do sleep 20; done`으로 걸어 두고 30분을 기다렸는데, PR은 `mergeStateStatus=DIRTY`(충돌)라 서버가 머지할 수 없는 상태였다. CI 3종은 전부 SUCCESS라 「곧 되겠지」로 읽혔고, **사용자가 「30분 지났는데 아직이야?」라고 묻기 전까지 나는 계속 기다리고 있었다** — **침묵한 실패**. / 원인: 두 사례의 방향이 반대인데 뿌리는 하나다 — **종료 조건이 상태 공간을 덮지 않는다**. ①은 실패 판정식이 환경에서 작동하지 않아 늘 참이었고(계측기 자체가 고장), ②는 실패 상태를 아예 안 봤다(성공만 겨눔). 특히 ②가 위험한 것은 **「아직 안 끝남」과 「영영 안 끝남」이 같은 얼굴**이기 때문이다 — 대기는 원래 조용한 일이라 이상 신호가 없다. CI가 초록인 것도 오독을 도왔다: **체크 통과와 머지 가능은 다른 축**인데(DIRTY는 체크와 무관하다) 초록을 「진행 중」의 근거로 썼다. / 해결: 종료 조건에 **성공 · 알려진 실패 · 조회 실패 · 타임아웃**을 모두 넣었다. PR 대기는 `MERGED`(성공) / `DIRTY`·`BEHIND`(막힘, 각각 처방이 다르다) / `CLOSED` / `gh` 조회 실패 / 20분 상한으로 갈라 **어느 쪽이든 말하고 끝나게** 했고, 서버 대기는 프로세스 검사를 걷고 **로그 파일에서 성공·실패 문자열을 직접 보는** 방식으로 바꿨다(`Started …` / `Application run failed`·`BUILD FAILED`). / 재발방지: ① **루프를 짜기 전에 「이 조건이 영영 안 오면 어떻게 알게 되는가」를 한 문장으로 답한다** — 답이 없으면 그 루프는 계측기가 아니라 희망이다. ② **실패 판정식은 그 환경에서 실제로 도는지 먼저 확인한다** — `pgrep`·`timeout`·`ps` 같은 것은 Git Bash에 없거나 다르게 동작한다(없는 명령은 「거짓」이 아니라 **비정상 종료**라 `!`를 붙이면 항상 참이 된다). ③ **하드 타임아웃을 항상 건다** — 상한이 있으면 최악이 「모르고 영영 기다림」에서 「N분 뒤 모른다고 말함」으로 바뀐다. ④ **초록 신호를 「진행 중」의 근거로 쓰지 않는다** — 축이 다른 지표는 서로를 보증하지 않는다(CI 통과 ≠ 머지 가능). / **관련**: T-083 군(`pr-merge.sh` — **이번 ②가 9회차다**. 특히 T-102 「하드픽스 안 쓰고 손수 워처 → DIRTY 누락」의 반복인데, 이번엔 `--arm`까지는 스크립트를 썼고 **그 뒤 완료 확인만 손수 루프로** 짜서 같은 구멍에 빠졌다 — 도구를 썼다는 사실이 그 도구가 안 덮는 단계를 안전하게 만들어 주지 않는다) · 글로벌 「통과는 증거가 아니다」의 시간축 판(여기선 **침묵**이 통과 행세를 한다)
