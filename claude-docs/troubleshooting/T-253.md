# T-253 · 같은 파일을 연속으로 고치는 두 PR에서, 뒤 PR의 리베이스 충돌을 「들어오는 쪽」으로 풀면 앞 PR의 규칙과 그 규칙을 지키던 테스트가 한 헝크에서 함께 사라진다 — 스위트는 초록인 채로 방어만 되돌아간다

**1회차** / 증상: `#1180`(게스트 뉴스 사건 묶기)을 먼저 머지된 `#1179`(스팸 출처 차단) 위로 리베이스하자 `GeneralBookNewsFeed.java`의 필터 파이프라인 한 자리에서 충돌했다. 흔한 해소인 「들어오는 쪽(내 브랜치) 채택」을 리뷰가 재현해 보니 `trustedSource`·`BLOCKED_SOURCES`·도박어 4종이 지워지고 **그것들을 잡던 `#1179` 테스트 4건도 같은 헝크에서 함께** 지워져, 전 스위트가 초록인 채로 운영 스냅샷 29건이 **전부 통과**(= 스팸 방어 이전 상태)로 돌아갔다. / 원인: 규칙(코드)과 그 계측기(테스트)가 **같은 브랜치의 한 쌍**이다. 충돌 해소가 브랜치 단위로 한쪽을 버리면 「규칙」과 「규칙의 부재를 잡을 단언」이 **동시에** 없어지므로, 남은 게이트는 원리상 침묵한다. 초록은 「규칙이 산다」가 아니라 「규칙을 묻는 사람이 없다」를 뜻했다. 리베이스가 만드는 「테스트가 자기 감시 대상과 함께 사라지는」 자리는 같은 파일을 연속으로 고치는 PR 쌍에서만 생긴다. / 해결: 양쪽을 다 남겨 해소하고, 해소 결과를 **앞 PR의 식별자 개수로** 확인했다 — `trustedSource` 참조 3건 · 탈락 매체명 로그 1건 · 운영 스냅샷 재생 단언이 `hasSize(23)`(`#1179`만) → `hasSize(20)`(둘 다). 배포 후 운영 응답에서도 도박어 0건으로 재확인(2026-09-22). / 재발방지: ① 같은 파일을 건드리는 연속 PR의 리베이스에서 충돌은 **「어느 쪽을 택할까」가 아니라 「양쪽 규칙이 다 살아 있나」**로 푼다 ② 해소 직후 `git diff origin/main -- <그 파일>`로 **앞 PR이 넣은 식별자를 이름으로 센다** — 테스트 초록은 증거가 아니다(테스트도 같이 사라진다) ③ 앞 PR의 테스트 건수를 **숫자로 알고** 리베이스에 들어간다(줄면 즉시 보인다). / **관련**: T-210(같은 rebase에서 `merge=union`이 changelog 행을 **둘 다 남기는** 반대 증상 — 뿌리는 같다: 리베이스의 자동 해소가 「무엇을 지켜야 하는가」를 모른다) · 「통과는 증거가 아니다」(계측기가 데이터·코드와 함께 사라지면 통과 쪽으로 고장 난다)
