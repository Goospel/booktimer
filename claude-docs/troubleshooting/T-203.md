# T-203 · 규칙을 설명하는 주석이 그 규칙의 소스 계측을 깨뜨린다 — 좋은 주석일수록 위험하다

증상: 구현을 올바르게 고쳤는데도 **소스를 문자열로 계측하는 테스트가 붉어진다**. 같은 날 두 번 밟았다 — css 전환 규칙(#915)에선 셀렉터를 클래스 밖으로 옮겼는데도 `reading-lamp`가 남았다고 실패했고, 여백 진입 게이트(#917)에선 여는 호출을 `openMargin` 하나로 모았는데도 「2개」로 셌다. 테스트가 거짓으로 붉어 구현을 의심하게 되는 것이 이 함정의 비용이다. / 원인: 그 규칙을 **설명하는 주석**이 규칙의 대상 문자열을 예시로 포함한다 (css: `⚠️ 셀렉터에 .reading-lamp를 넣지 않는다` / ts: `여는 호출(setMargin({…}))이 여기 말고 없는지 계측한다`). 정규식은 주석과 코드를 구분하지 못한다. 특히 css 셀렉터 매칭 `[^{}]+\{`는 **주석에 중괄호가 없어 직전 주석 블록을 통째로 빨아들인다** — 셀렉터만 보았다고 생각한 것이 사실은 「주석 + 셀렉터」였다. / 해결: 계측 전에 주석을 걷는다. css는 `.replace(/\/\*[\s\S]*?\*\//g, '')`, ts/js는 거기에 `.replace(/\/\/.*/g, '')`를 더한다 (기본 `.`가 개행을 안 먹으므로 한 줄 주석에 딱 맞다 — `[^
]`을 쓰려다 이스케이프가 꼬여 **정규식이 통째로 깨져 테스트 파일이 파싱조차 안 된** 적이 있다). / 재발방지: ① **좋은 주석일수록 위험하다** — 규칙을 정확히 설명할수록 대상 문자열을 그대로 적게 된다. 주석을 줄여 설명을 죽이는 것이 아니라 **계측이 주석을 걷는다**. ② 소스를 문자열로 계측하는 테스트를 새로 쓸 때 주석 제거를 **기본 절차**로 넣는다. ③ 개수 단언(`toHaveLength(1)`)은 주석 오염에 특히 취약하다 — 하나 늘어난 것이 코드인지 설명인지를 구분 못 한다. ④ 이 레포는 소스 문자열 계측을 반복해 쓴다(css 셀렉터 실재 · js 클래스 실재 · 진입점 단일화) — **3회차가 나오면 `readSourceWithoutComments()` 공용 헬퍼로 승격**한다(지금은 두 곳뿐이라 각자 처리). **2회차** — 한 세션 안에서 연달아 밟았고, 둘 다 「규칙을 주석으로 잘 설명한 것」이 원인이었다
