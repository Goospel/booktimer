# T-272 · Git Bash `grep -c $'\r$'`는 줄끝 계측기가 아니다 — 직접은 CR을 떼고, `"$(…)"` 안에서는 모든 줄에 맞는다

**증상**: 설계 문서 두 개를 고치기 전 BOM·EOL 보존(글로벌 CLAUDE.md 인코딩 원칙 3)을 확인하려고 `grep -c $'\r$' "$f"`와 `wc -l`을 비교했다. 결과가 거꾸로 나왔다.
- LF 파일 `2026-10-17-booktimer-app-v1.md`(CR 0바이트)는 `CRLF줄=2054 전체줄=2054`로 나왔다.
- 작업 트리에서 CRLF인 `plan.md`(CR 6097 · LF 6097 — core.autocrlf=true)는 `CRLF 0`으로 나왔다.
- 반영을 맡은 서브에이전트는 Python 바이트 판정으로 「원본은 LF」라고 맞게 보고했다. 반면 diff 검증 서브에이전트는 같은 `grep -c $'\r$'`로 「CRLF 2157 = 2157, 형식 OK」를 냈다. 결론(줄끝 보존)은 우연히 맞았지만 근거가 틀린 통과였다.

**원인**(대조 파일 실측 — 이 머신 Git Bash, GNU grep 3.0. `eol-lf.txt` = `a\nb\nc\n`, `eol-crlf.txt` = `a\r\nb\r\nc\r\n`)

| 명령 | LF 파일 | CRLF 파일 |
|---|---|---|
| `grep -c $'\r$' f` (직접) | 0 | **0** |
| `printf … "$(grep -c $'\r$' "$f")"` (`"$(…)"` 안) | **3** | 3 |
| `grep -U -c "<CR>$" f` | 0 | 3 |
| `tr -cd '\r' < f \| wc -c` | 0 | 3 |

- **직접**: Git Bash의 grep은 `-U`(binary) 없이 열면 줄끝 CR을 떼고 맞춘다 → CRLF 파일에서도 `\r$`가 맞지 않는다.
- **`"$(…)"` 안**: 같은 `$'\r$'`가 모든 줄에 맞았다(LF 파일 포함). Bash 도구가 이 꼴을 감싸 돌릴 때의 따옴표 처리로 패턴이 바뀌는 것으로 보인다(미확인). 같은 줄에 `$'\r$'`를 두 번 쓴 명령은 `unexpected EOF while looking for matching ')'`로 아예 파싱되지 않기도 했다.
- 두 경우 모두 양성 대조군(CR이 있는 걸 아는 파일)을 같이 돌리지 않으면 숫자가 그럴듯해 보인다. 「통과는 증거가 아니다」의 계측기 고장이다.

**해결**: CR은 바이트로 센다.
- 셸: `tr -cd '\r' < f | wc -c` / `tr -cd '\n' < f | wc -c`. CR 수가 LF 수와 같으면 CRLF, 0이면 LF다.
- 또는 `node -e` / Python으로 바이트 13·10을 센다.
- grep을 꼭 써야 하면 `-U`를 붙이고, CR은 `$'\r'` 대신 `CR=$(printf '\r')`로 만든 변수를 넘긴다.

**재발방지**
- 줄끝 판정 명령에는 양성 대조(CRLF로 아는 파일 하나)를 같이 돌린다. 줄끝 확인을 서브에이전트에 맡길 때는 브리프에 「`grep -c $'\r$'` 금지, `tr -cd '\r' | wc -c`」를 적는다.
- 하드 가드는 아직 없다. hookify 룰(Bash 명령에 `grep` + `\r$`가 있고 `-U`가 없으면 경고)은 제안 단계다. 글로벌 규칙 추가라 사용자 승인 뒤 `/hookify`로 넣는다. 2회차가 오면 그 룰을 먼저 넣는다.
