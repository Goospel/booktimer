# T-168 · Hibernate 생성 스키마로 도는 테스트는 JPA 미매핑 테이블을 못 본다 — Flyway 전용 테이블의 FK 결함은 전 스위트 그린인 채로 운영에서 터진다

증상: 겉으로는 완전히 정상이다. 전체 테스트 1609건 그린, `AccountDeletionIntegrationTest`(H2 통합, 책·신고·목표이력·용서권·미니앱 다갈래 자식까지 만드는)도 그린, CI·배포 전부 초록. 그런데 **운영에서 특정 사용자가 탈퇴 버튼을 누르면 FK 제약 위반으로 실패**한다 — 실측 27명 중 2명. 어느 테스트도 이 사용자를 표현하지 못해 신호가 0이다. / 원인: 두 겹이다. ① `AccountService.purge()`가 users를 FK 참조하는 테이블 중 넷(`author_affection`·`garden_placement`·`garden_decoration_placement`·`push_subscriptions`)을 안 지우는데 **전 FK가 `NO ACTION`**이라 DB가 대신 지워주지 않는다. ② **그걸 잡아야 할 테스트가 구조적으로 못 잡는다** — 메인 스위트는 `ddl-auto=create-drop`이라 H2 스키마를 **엔티티 매핑에서** 만든다. 그런데 죽은 셋은 자바 코드가 한 번도 참조하지 않는 **Flyway 전용 테이블**이라 테스트 DB에 **아예 존재하지 않는다**. 존재하지 않는 테이블의 FK는 위반될 수도 없으니 통합테스트가 100% 통과한다. 남은 `author_affection`은 매핑돼 있지만, 기존 통합테스트가 자식 픽스처를 **손으로 골라** 만드는 방식이라 목록에 없어 그냥 안 보였다. ⚠️ **이 트랩군의 2회차 승격(T-023·T-029 → prose 「부모 삭제 경로는 H2 통합테스트 필수」)이 부족했다는 것이 핵심 교훈이다** — 시킨 대로 통합테스트가 있었는데도 뚫렸다. / 해결: 처리를 둘로 가른다 — 살아있는 `author_affection`은 `deleteByUser`를 만들어 `purge()`에 넣고, 죽은 셋은 **`V68`로 DROP**한다(죽은 것을 위해 삭제 코드를 새로 쓰지 않는다). 회귀 가드는 **`FlywayMigrationTest`**(실 마이그레이션을 도는 유일한 테스트)에 둔다: 「users를 FK 참조하는 테이블 집합 == `purge()`가 지우는 집합」을 `INFORMATION_SCHEMA` 질의로 뽑아 **양방향** 단언(FK가 새로 생겼는데 purge에 없어도, 목록에만 있고 스키마에 없어도 실패). / 재발방지: ① **테스트 DB의 스키마가 어디서 오는지 확인해라** — `ddl-auto`로 만든 스키마는 «엔티티의 그림자»지 운영 스키마가 아니다. 운영에만 있는 테이블·컬럼·제약은 그 스위트에서 **존재하지 않으므로 위반될 수도 없다**(무성 그린). 마이그레이션이 진실이면 마이그레이션을 도는 테스트에서 검증해라. ② **「자식 픽스처를 손으로 골라 만드는」 삭제 테스트는 목록 밖을 영원히 못 본다** — 목록을 늘리는 대신 **스키마에서 파생되는** 단언으로 바꿔라. 사람이 유지하는 목록과 DB가 유지하는 목록을 **대조**하는 것이 요점이다. ③ **cascade 없는 FK는 애플리케이션이 전량 책임진다** — `NO ACTION`이면 하나만 빠져도 그 부모는 영원히 못 지운다. FK를 새로 만들 때 삭제 경로를 같은 PR에서 잇거나, 위 대조 테스트가 강제하게 해라. ④ **죽은 테이블에 산 FK가 달려 있으면 그건 좀비가 아니라 지뢰다** — 코드가 참조를 안 해도 제약은 살아서 남의 동작을 막는다. 은퇴시킬 땐 테이블까지 DROP해라. ⑤ 이 결함은 **사용자 제보로도 잘 안 온다** — 탈퇴는 실패하면 사용자가 그냥 떠난다. 3회차(T-023 · T-029 재발, 2회차 승격 prose로는 불충분해 하드픽스로 재승격). 운영 테스트 계정 삭제 작업 중 FK 목록을 훑다 실측으로 발견
