# T-243 · CP949 stdin 회귀를 겨눈 훅 테스트가 한글을 넣고도 공허했다 — 깨짐은 한글 「길이」가 아니라 마지막 글자의 끝바이트로 갈리고, 「가」·「한글메모」 픽스처는 CP949로 읽어도 파싱이 안 깨진다

**1회차(「공허한 테스트」 군 9회차)** / 증상: 훅이 stdin을 `[Console]::In`으로 읽어 한글 섞인 명령에서 게이트가 fail-open 되는지 재현하려고 「가」를 길이 0~52로 늘린 11종 + 한글 위치 3곳×길이 6종, 총 29조합을 넣었는데 전부 정상 차단(exit 2)이라 「재현 안 됨」으로 끝날 뻔했다. `block-main-push` 테스트 Case 9(`echo 한글메모 && git push origin main`)는 주석에 「CP949로 읽으면 fail-open 될 수 있다 — 그 회귀를 잡는다」고 적혀 있었는데 수정 전 코드에서도 초록이었고, `check-commit-message` Case 4(「한글 제목」)도 깨진 글자가 우연히 U+AC00~D7A3에 떨어져 초록이었다. / 원인: .NET CP949 디코더는 선행바이트(0x81~0xFE)를 만나면 뒤 바이트가 무엇이든 둘을 한 글자로 먹는다. UTF-8 한글은 3바이트라 짝짓기 정렬이 글자마다 밀리고, 한글 바로 뒤가 `"`·`\`일 때 **정렬상 홀로 남은 마지막 바이트가 선행바이트면** 따옴표를 삼켜 JSON이 깨진다(`{"a":"문"}` → `… 81FE 003F 007D`). 「가」(EA B0 **80**)는 0x80이 선행바이트가 아니라 정렬이 매번 리셋되고, 「한글메모」 뒤는 공백이라 삼켜도 무해하다 — 「문」(EB AC **B8**)·「테스트」·「독서 기록 테스트」는 깨진다. 파싱이 성공해도 오해석 글자가 한글 음절 블록 밖이면 `\p{IsHangulSyllables}` 감지가 빗나간다(`-m "feat: 가"`가 통과). / 해결: 훅 9개를 `StreamReader(OpenStandardInput(), UTF8Encoding($false))`로 바꾸고(#1119 게이트 6종 · #1121 세션 훅 3종), 각 테스트에 **따옴표 바로 앞 「테스트」/「문」** 케이스를 넣어 수정 전 코드에서 붉어지는 것을 확인했다(Red 6+2건). `cwd`를 쓰는 세션 훅은 폴백이 우연히 통과하지 않게 고유 브랜치명·비-git 실행 폴더로 단언했다. / 재발방지: ① 인코딩 회귀 테스트의 한글 픽스처는 **수정 전 코드에서 붉어지는지 먼저 보고** 고른다 — 한글이 들어 있다는 것만으로는 대조군이 아니다. ② 디코딩을 의심하면 훅을 돌리기 전에 코드포인트를 덤프한다(`$raw.ToCharArray() | % { '{0:X4}' -f [int]$_ }`) — 따옴표(0022)가 사라졌는지가 한 줄로 보인다. / **관련**: 글로벌 「Windows 셸 원칙」·hookify `warn-console-in-stdin`(그 룰 본문의 「내용에 따라 갈려 예측 불가」는 실은 끝바이트 규칙으로 예측 가능하다 — 글로벌 문서 정정 후보) · 글로벌 「통과는 증거가 아니다」(판별력을 죽인 것은 단정이 아니라 데이터) · T-242(같은 훅들의 다른 사각 — 명령 속 `cd`).
