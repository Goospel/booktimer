# T-161 · 메인 테스트 스위트의 H2 스키마엔 마이그레이션의 유니크·CHECK 제약이 없다 — 그 제약을 겨눈 테스트는 제약을 지워도 안 깨지는 공허한 테스트가 된다

증상: 미니앱 핸들 만들기 설계가 "H2 통합 테스트가 실 DB CHECK·유니크 제약을 탄다"는 전제로 「DB CHECK 실측」 테스트를 지시했는데, 구현 단계에서 확인하니 `uk_users_login_id`도 `ck_users_login_id_when_onboarded`도 **테스트 스키마에 아예 존재하지 않았다**. 그대로 썼다면 통과하되 아무것도 증명하지 못하는 테스트가 남았을 것이다(작성 전에 발각 — 약 10분 소요). / 원인: `src/test/resources/application.properties`가 `spring.flyway.enabled=false` + `spring.jpa.hibernate.ddl-auto=create-drop`이라, 메인 스위트의 스키마는 Flyway 마이그레이션이 아니라 **Hibernate가 엔티티 선언에서** 만든다. `User` 엔티티의 `@Table(uniqueConstraints=…)`엔 `uk_users_email` **하나뿐**이고, `uk_users_login_id`(V13)·V15 CHECK는 `db/migration/*.sql`에만 산다. 즉 **운영 MySQL엔 있고 테스트 H2엔 없다** — 제약을 겨눈 단언은 계측기의 관측 불가 영역에 정확히 들어간다(T-149와 같은 구조, 사각의 위치만 하니스→스키마로 옮겨간 것). / 해결: 그 테스트를 만들지 않고, 성공 케이스에서 `flush()`로 쓰기가 DB까지 도달하는지만 단언했다. 부수 실측: **테스트 환경에서 중복 핸들 409의 방어선은 DB 유니크가 아니라 서비스 사전확인(`existsByLoginId`) 단독**이다(그 한 줄을 지우는 돌연변이로 확인 — RED). 운영에서는 DB 유니크가 최종 방어선이라 계층이 하나 더 있다. / 재발방지: ① **마이그레이션에만 있는 제약(유니크·CHECK·FK·인덱스)을 겨눈 테스트는 메인 스위트에서 공허하다** — 쓰기 전에 그 제약이 **엔티티 선언에 있는지** 확인한다(있으면 create-drop 스키마에도 생긴다). ② 마이그레이션 자체를 검증할 자리는 `FlywayMigrationTest`(flyway 켜진 별도 격리 DB)다 — 일반 통합 테스트에 그 역할을 기대하지 않는다. ③ **설계 문서가 "H2가 실 DB 제약을 탄다"고 적으면 그 전제부터 의심한다** — 이번엔 설계(designer)가 틀린 전제를 깔았고 구현(implementer)이 코드로 확인해 걸렀다. 「공허한 테스트」군 **4회차**(T-144·T-145·T-149) — 트래커 갱신. 다만 앞 3건은 돌연변이 확인이 잡았고 이번은 **설계 전제 검증**이 잡았다. 미니앱 핸들 만들기 구현 중 발생
