# T-235 · 커밋 테스트 게이트가 8분에 걸려 `.java`가 든 커밋이 전부 막혔다 — 훅 메시지의 「경합」 단정에 두 번 헛짚었고, 그다음엔 내가 1회 측정으로 「스위트가 예산 추월」이라 단정했다가 대조군에서 뒤집혔다**) / **1회차**(T-078 하드픽스의 부작용) / 증상: `git commit`이 8분 뒤 `[BLOCKED] Test gate exceeded 8 min -- commit aborted (likely gradle daemon/lock contention, T-078)`로 차단됐다. 훅이 프로세스 트리를 `taskkill /T`하고 `gradlew --stop`까지 돌린 **직후**라 상태는 깨끗했고(`java` 프로세스 0 · 8080 미점유 — 둘 다 확인), 그대로 재시도했는데 **같은 자리에서 또** 8분에 막혔다. / 원인: 게이트 밖에서 `./gradlew test`를 직접 재니 **9분 6초 · BUILD SUCCESSFUL**. 경합이 아니라 **스위트 자체가 게이트 예산(8분)을 넘긴 것**이다. 그 8분은 T-078이 45분 freeze를 막으려 세운 상한인데 그 뒤 테스트가 자라 상한을 추월했다 — 하드픽스가 「무한 hang을 막는」 쪽에서 「정상 빌드를 죽이는」 쪽으로 넘어간 자리다. ⚠️ 두 번 헛짚은 이유는 **메시지가 원인을 단정**했기 때문이다: 「likely … contention」을 읽고 경합만 확인했고(0건), 그 결과가 「경합이 아니다」까지는 알려줘도 「그럼 뭐냐」로는 안 이어졌다. **자가복구 메시지는 진단을 한 방향으로 몰 수 있다 — 죽은 원인 하나를 배제했으면 메시지 밖을 본다.

해결: 게이트 밖에서 `./gradlew test`를 **한 번 완주**시키면 gradle이 `test`를 up-to-date로 표시하므로, 소스를 더 안 건드린 채 커밋하면 게이트가 즉시 통과한다(실제로 이렇게 통과시켰다). 급하면 `BOOKTIMER_TEST_GATE_TIMEOUT_MS`로 상한을 올린다(훅이 이미 읽는 환경변수). / 재발방지: **「테스트 게이트 타임아웃」을 보면 경합을 의심하기 전에 `./gradlew test`의 실제 소요부터 잰다** — 1회 측정으로 갈리고, 두 원인의 처방이 정반대다(경합=죽이고 재시도 / 초과=상한 조정·스위트 단축). ⏸ 상한 상향과 메시지 문구(「원인이 둘」로) 수정은 훅 변경이라 별건으로 남긴다 — 다만 **9분짜리 게이트를 매 커밋 무는 것 자체가 다음 결정 대상**이다(CI가 PR에서 같은 테스트를 돌린다). / ⚠️ **곁다리(같은 날, 병렬화 측정 중 실측) — 자가복구의 `gradlew --stop`은 이 머신의 모든 데몬에 간다.** 워크트리가 4개인데 다른 세션이 이 게이트에 걸리자 **그쪽 훅이 쏜 stop이 내 정상 빌드를 끊었다**(`Gradle build daemon has been stopped: stop command received` · 71초 만에 exit 1 · 「8 stopped Daemons could not be reused」가 흔적). 즉 **스위트가 예산을 넘긴 상태에서는 T-078이 막으려던 「멀티세션 데몬 경합」을 훅 자신이 재생산한다** — A가 8분에 걸려 stop을 쏘고 → B의 정상 빌드가 죽고 → B도 재시도하다 같은 곳에 걸린다. 자가복구는 자기 세션만 복구한다고 **가정**하지만 gradle 데몬은 머신 전역 자원이다. 상한 상향·스위트 단축이 이 고리도 함께 끊는다(발동 자체가 줄어서). ⚠️ 이 곁다리 탓에 **측정이 조용히 오염된다** — 병렬화 효과를 재던 실행이 71초에 죽었는데, 그 숫자만 보면 「병렬화가 빨라졌다」로 읽힌다. 남이 죽인 실행과 정상 완주는 **소요만으로 구별되지 않는다**(`BUILD SUCCESSFUL` 유무로 가른다). / ⚠️ **정정(같은 날 저녁, 대조군 측정) — 위 「원인」이 틀렸다.** 병렬 실행(`maxParallelForks=4`)으로 줄여 보려고 대조군을 세웠더니 **같은 스위트가 순차로 3분 23초**였다(2,206건 · `BUILD SUCCESSFUL`). 병렬 4-fork는 3분 28초로 **차이가 없다**(되레 5초 느리다 — CPU 시간 합 728초가 벽시계 208초에 겹쳐 들어갔으니 fork는 실제로 일했다. **병목이 CPU가 아니라는 뜻**이다). 그 사이 다른 세션이 #1070으로 테스트 83건(3.6%)을 지웠지만 **컨텍스트 수는 31로 그대로**고, 3.6%로 2.7배를 설명할 수 없다. **9분 6초는 재현되지 않았고 원인은 미확정이다** — 그 실행이 무엇과 경합했는지(다른 세션의 빌드 · 실시간 검사 · 콜드 파일캐시) 사후에 알 길이 없다. 확실한 것은 셋뿐이다: ⓐ 지금 이 스위트는 **3분 23초**다 ⓑ **병렬화는 답이 아니다**(그래서 `build.gradle` 변경은 폐기했다 — 효과 없는 설정을 남기면 다음 사람이 그것을 「이미 최적화됨」으로 읽는다) ⓒ **1회 측정으로 원인을 단정한 것이 이 항목의 진짜 실수다** — 「소요부터 재라」는 처방을 스스로 적어 놓고 그 처방으로 얻은 **한 번의 값**에 또 기댔다. **성능 원인은 재현부터 시킨다**(같은 조건 2회 + 대조군). 앞의 「훅 메시지가 원인을 단정해 헛짚었다」와 같은 고장을 이번엔 **내가 냈다**. ⏸ 상한 상향은 당분간 불필요하다(3분 23초 < 8분) — 다시 8분에 닿으면 그때는 원인 단정 전에 **재현 여부부터** 본다. / **관련**: T-078(이 상한을 세운 하드픽스 — 이 항목은 그 승격의 만료다) · 「통과는 증거가 아니다」의 사촌(여기선 **차단 메시지**가 증거로 오인됐고, 곁다리에선 **짧은 소요**가 그럴 뻔했다) / **2회차(2026-09-11, `#1088` 서버 커밋 — 구현 서브에이전트 실측)**: 같은 메시지로 8분에 막혔고, 데몬·8080 잔재 0을 확인한 뒤 게이트 밖 `./gradlew test`가 **8분 19초 · BUILD SUCCESSFUL** — 위 처방(1회 완주 → up-to-date → 커밋)으로 통과. 이번에도 **1회 측정**이라 원인은 여전히 미확정이다(정정 절의 3분 23초와 2.5배 차이 — 같은 스위트가 조건에 따라 8분을 넘나든다는 것만 확실). 2회째라 트래커에 올렸다 — 승격은 3회째에. / **3회차(2026-09-21, `#1180` 리뷰 반영 커밋)**: 같은 메시지로 8분에 막혔고, 게이트 밖 `./gradlew test`가 **13분 13초 · 2669건 통과**였다 — 1·2회차(3분 23초 / 8분 19초 / 9분 6초)보다 또 늘었다. 처방대로 완주 후 재시도해 up-to-date 빌드로 통과했고 `SKIP_TESTS`는 쓰지 않았다. **3회째라 트래커의 예고대로 승격이 걸렸다** — `BOOKTIMER_TEST_GATE_TIMEOUT_MS` 상향(또는 게이트를 변경 모듈 테스트로 축소) + 훅 메시지의 「likely gradle daemon/lock contention」 단정을 「원인이 둘: 경합 또는 스위트 성장」으로 고치는 훅 변경 PR이 남았다.
