# T-236 · `\uXXXX` 손 인코딩으로 쓴 한글은 한 음절만 어긋나도 에러 없이 통과한다 — 사용자 대면 랜딩 카피가 「쌓입니다」→「쌓팥니다」로 배포 직전까지 갔다

증상: 서재 캐릭터 폐기 PR-1에서 랜딩 카피를 고치며 리터럴 대신 `\uXXXX` 이스케이프로 한글을 적어 넣었는데, 코드포인트가 어긋나 `landing.html`의 「책장에 쌓입니다」가 「책장에 쌓팥니다」로 저장됐다(2곳). `./gradlew test` 2,211건·vitest 598건·커밋 훅·CI 4체크가 **전부 초록**이었고 `LandingPageTest`도 그 문장을 단언하지 않아 통과했다. 구현자가 diff의 한글 추가 줄을 전수 감사해 잡았지만(감사 대상 줄 수는 구현자 68건·리뷰어 88건으로 보고가 갈린다 — 내가 재측정하지 않았다), 그 감사를 안 했으면 운영 랜딩 페이지에 그대로 배포됐다. plan.md에도 같은 원인으로 3곳이 깨져 있었다. / 원인: 손으로 적은 유니코드 이스케이프는 **틀려도 여전히 유효한 한글 음절**이 된다 — 문법 오류가 아니라 그냥 다른 글자다. 그래서 파서·린터·테스트·훅 어디에도 안 걸린다. 게다가 소스가 이스케이프 나열이라 사람 눈으로 읽히지 않아, 렌더된 결과를 따로 보지 않으면 확인할 길이 없다. ⚠️ 글로벌 「Windows 셸 한글·인코딩 원칙」이 덮는 두 함정(Git Bash grep의 C 로케일 무성 실패 · PowerShell 5.1 인라인 인자의 CP949 깨짐)과 **메커니즘이 다르다** — 그쪽은 도구가 멀쩡한 입력을 깨뜨리는 것이고, 이쪽은 **쓰는 쪽이 애초에 다른 글자를 적는** 것이라 도구를 아무리 바꿔도 안 막힌다. / 해결: 한글은 이스케이프하지 말고 히어독·Write·Edit 도구로 **리터럴 그대로** 넣는다. 이번엔 전 diff의 한글 추가 줄을 전수로 눈으로 읽어 5곳(랜딩 2 + plan 3)을 고쳤다. / 재발방지: ① 사용자 대면 문구(템플릿 카피·UI 문자열·커밋 메시지·changelog·문서)에 `\uXXXX`를 쓰지 않는다 — 리터럴이 원칙이고, Write/Edit 도구는 UTF-8을 정확히 쓴다. ② 부득이 이스케이프를 썼으면 커밋 전에 `git diff`의 **한글 추가 줄을 전수로 눈으로 읽는다**. 자동 검사에 기대지 마라 — 유효한 글자라 원리상 아무 계측기에도 안 걸린다. ③ 「통과는 증거가 아니다」의 한 갈래다: 초록은 「문법이 맞다」만 말하고 「뜻이 맞다」는 말하지 않는다. 사람이 읽어야만 판정되는 축이 있다는 것을 인정하고 그 축엔 눈을 배정한다. 1회차 신규 — 재발·승격 트래커에는 올리지 않는다(2회째에 군으로 묶는다)
