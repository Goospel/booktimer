# T-169 · 마이그레이션에만 있는 제약은 메인 스위트에 존재하지 않는다 — 그 자리에 둔 테스트는 영영 초록이 안 된다

증상: 설계가 「UNIQUE 위반을 `UserRepositoryTest`(`@DataJpaTest`)에서 단언하라」고 지정했고 그대로 넣어 돌리니 `Expecting code to raise a throwable` — 예외가 **아예 안 났다**. 구현이 틀린 것처럼 보이지만 마이그레이션도 엔티티도 정상이었다. / 원인: 메인 스위트는 `spring.flyway.enabled=false` + `ddl-auto=create-drop`이라 H2 스키마를 **엔티티 매핑에서** 만든다. 그런데 이 레포는 유니크를 엔티티 `@Table`에 선언하지 않고 **마이그레이션에만** 둔다(DB가 단일 출처 — 기존 `uk_users_login_id`도 동일). 따라서 슬라이스 스키마엔 그 제약이 아예 없고, **없는 제약은 위반될 수도 없다**. 슬라이스에서 두 사용자에게 같은 `previous_login_id`를 저장해도 예외 0인 것을 프로브로 실측했다. / 해결: 실제 Flyway가 도는 `FlywayMigrationTest`로 옮긴다(기존 email 유니크·V15 CHECK 검증이 사는 자리 = 관례에도 맞음). 돌연변이로 실효 확인 — `V69`의 UNIQUE 한 줄을 지우자 그 테스트만 정확히 깨졌다. / 재발방지: ① 제약·테이블을 추가했으면 **「그게 엔티티 매핑에 있나, 마이그레이션에만 있나」로 테스트 자리를 정한다** — 마이그레이션에만 있으면 `FlywayMigrationTest`. ② 새 테스트가 «구현이 없어서»가 아니라 «예외가 아예 안 나서» RED이면, 구현을 의심하기 전에 **그 스위트의 스키마 출처**를 먼저 본다. ③ 설계 문서가 테스트 자리를 지정했더라도 그 자리가 성립하는지는 구현이 실행으로 확인한다(이번엔 구현자가 그대로 넣어 돌려보고 잡았다 — 추측으로 옮겼으면 근거가 없었다). **2회차 = T-168 재발**(같은 뿌리의 「테이블」 면 — JPA 미매핑 테이블이 테스트 DB에 아예 없어 FK 결함이 무성 그린이었다. 이건 「제약」 면이다. 같은 날 다른 방향에서 두 번 밟았다) — 트래커에 신규 군 등재
