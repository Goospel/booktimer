# T-250 · `document.fonts.check`는 구글 폰트 한글에서 로드됐는데도 `false`를 준다 — 웹폰트 실적용은 폭 실측 + 음성 대조군으로 판정한다

**1회차** / 증상: 편집기 제목을 고운바탕 700으로 바꾼 뒤 브라우저에서 확인하니 `getComputedStyle`은 `font-family: "Gowun Batang"` / `font-weight: 700`을 정확히 돌려주는데 `document.fonts.check("700 26px 'Gowun Batang'")`가 **`false`**였다. 「선언은 됐지만 폰트가 안 왔다 → 폴백 serif로 그려지는 중」으로 읽혀, 멀쩡한 구현을 회귀로 오판하고 `@import`·CSP·네트워크를 뒤지러 갈 뻔했다. / 원인: 구글 폰트는 한글을 **수십~수백 개 유니코드 subset**으로 쪼개 배포한다(`unicode-range`별 `@font-face`). 그래서 `document.fonts`에 같은 `Gowun Batang 700`이 **100개 가까이** 등록되고, 그중 화면에 실제로 쓰인 글자가 속한 subset 몇 개만 `loaded`, 나머지는 `unloaded`로 남는다. `check()`는 **인자로 준 문자열(생략 시 기본 샘플)을 그리는 데 필요한 face가 전부 준비됐는지**를 보므로, 이 구조에서는 로드가 정상이어도 쉽게 false가 된다. 즉 이 계측기는 **실패 쪽으로 고장 난다** — 「통과는 증거가 아니다」 원칙이 경계하는 방향(통과 쪽 고장)의 **반대**라 더 눈에 안 띈다. `computedStyle`도 증거가 못 된다(그건 선언의 반영일 뿐 실제 렌더 서체가 아니다). / 해결: **같은 글자를 재서 폭을 비교**한다 — 숨긴 `<span>`에 `font: 700 26px <후보>`를 걸고 `getBoundingClientRect().width`를 읽는다. 이번 실측은 `'Gowun Batang', serif` 184.48px vs `serif` 203.4px로 갈렸고, **음성 대조군** `'NoSuchFontXyz', serif`가 `serif`와 **정확히 같은 203.4px**이라 「폴백이면 이 값이 나온다」가 고정됐다. 두 값이 다르면 그 서체가 실제로 로드돼 렌더 중이다. 보조 신호로 `[...document.fonts].map(f => f.status)`에 `700 loaded`가 하나라도 있는지 본다(없으면 진짜 미로드). / 재발방지: ① **웹폰트 실적용 판정에 `fonts.check`를 쓰지 않는다** — 폭 실측이 단일 처방이다. ② 대조군을 **양쪽** 잡는다: 후보 서체(양성)와 존재하지 않는 폰트→폴백(음성). 음성이 없으면 「폴백 값」을 모르니 폭 차이를 해석할 수 없다. ③ CSS 값 검사 테스트(`frontend/src/editorHeadingScale.test.ts`)는 서체 **선언**만 못 박으므로, 주석에 「음성 판정 전용」을 같은 줄에 적어 며칠 뒤의 자신이 「검사 통과 = 폰트 붙음」으로 읽지 않게 했다. / **관련**: T-153(검사가 통과 쪽으로 고장 나는 계열 — 이 항목은 그 **반대 방향** 사례
