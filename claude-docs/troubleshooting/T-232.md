# T-232 · Thymeleaf 템플릿 캐시가 기본 활성이라, `bootRun` 중 템플릿만 고치면 옛 화면이 그대로 나온다 — 증상이 「내 조건식이 틀렸나」로 읽혀 멀쩡한 코드를 고치게 만든다

**1회차** / 증상: 설정의 「토스 앱 연결」 카드에 딥링크 링크를 `th:if`로 새로 달고 로컬에서 확인했는데, 연결 코드를 발급한 직후에도 **링크가 0건**이었다(코드 알림은 정상 노출). 조건식을 의심해 `${... or tossLinkCode}` → `${... or tossLinkCode != null}`로 고쳤는데 **여전히 0건**. 서버를 재기동하니 **그 자리에서 1건**으로 떴다. / 원인: 이 레포엔 `spring.thymeleaf.cache` 설정이 **어디에도 없어** Spring Boot 기본값(`true`)이 그대로 산다 — `bootRun` 중 `templates/*.html`을 고쳐도 컴파일된 템플릿이 캐시에서 재사용된다. 정적 리소스(`static/**`)는 바로 반영되므로 **같은 세션에서 CSS·JS 변경은 즉시 보이고 템플릿만 안 보이는** 비대칭이 생기고, 그게 「내 HTML은 반영됐는데(파일 크기도 늘었는데) 조건만 안 먹는다」는 오독을 만든다. ⚠️ 실제로 그 오독이 **2차 피해를 냈다**: 캐시를 의심하지 않고 조건식을 고쳤고, 그 고친 식(`${tossLinked or ...}`)이 CI에서 `SpelEvaluationException`으로 터졌다(`tossLinked`가 null인 검증 실패 경로 — `th:if` 단독은 null을 false로 넘기지만 **`or`의 피연산자로는 그렇지 않다**). null 결함은 첫 조건식부터 있던 별건이지만, **캐시 오진이 없었다면 그 자리를 그렇게 급히 건드리지 않았다.** / 해결: 템플릿을 고쳤으면 **재기동하고 나서** 검증한다. 재기동 후 딥링크·코드 알림이 모두 1건으로 확인됐고, null 결함은 `${tossLinked == true or ...}`로 따로 고쳤다. / 재발방지: **「화면이 예상과 다르다」를 만나면 코드를 고치기 전에 「내가 고친 그 코드가 지금 서빙되고 있는가」부터 묻는다.** 이 레포에서 「고쳤는데 안 바뀐다」를 만드는 층이 셋이고 각각 해제법이 다르다 — ① **템플릿**(서버 캐시 → 재기동) ② **프론트 번들**(`npm --prefix frontend run build` 필요 — T-063) ③ **정적 파일**(브라우저 캐시 → 강제 새로고침). 이 중 ①만 「파일을 고쳤는데 아무 신호도 없이 옛것이 나오는」 얼굴이라 가장 오래 속인다. ⚠️ 그리고 **오진 상태에서 고친 코드는 되돌려 확인한다** — 이번에 「`or tossLinkCode`가 정말 안 되는지」는 끝내 확정하지 못했다(캐시와 함께 반영돼 대조군이 없다). / **관련**: 글로벌 「이상값을 만나면 앱보다 관측 경로를 먼저 의심한다」의 **서버사이드판**(그쪽은 브라우저 탭·CDP, 이쪽은 서버 캐시) · T-063(번들 재빌드 — 같은 「안 바뀐다」 가족) · 같은 세션의 곁다리: `curl -L -X POST`가 리다이렉트를 POST로 따라가 엉뚱한 핸들러를 쳐 **403을 만들어 냈다**(서버는 302로 정상이었다) — 일반 curl 지식이라 별도 항목으로 두지 않되, **관측 도구가 만들어 낸 증상**이라는 점에서 이 항목과 한 몸이다.
