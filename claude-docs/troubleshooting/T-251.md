# T-251 · 브라우저 실측에서 서비스워커가 옛 번들을 먹여 「고친 게 안 먹었다」는 거짓 판정을 만든다 — 차단은 첫 이동이 아니라 매 이동에 건다

**1회차** / 증상: #1147의 첫 페인트 수정을 확인하는데 20ms 간격 샘플링이 고치기 전과 똑같은 구간(112~354ms `data-mode=reading`)을 그대로 냈다. 수정은 실제로 코드에 들어가 있었고 서버도 새 파일을 서빙하고 있었다. / 원인: `navigate_page`의 `initScript`는 **그 내비게이션에만** 적용된다. 첫 이동에서만 서비스워커 등록을 막아 두면 이후 이동에서 페이지가 `sw.js`를 다시 등록하고, 그 캐시(`shell-v8`)가 옛 `dashboard/dashboard.js`를 돌려준다. 페이지가 받은 번들은 **613,132자**, 레포 파일은 **613,143자**(11자 차이). / 감별에서 두 번째로 틀릴 뻔한 것: `fetch(...).then(r => r.text()).length`는 **문자 수**이고 `wc -c`·파일 크기는 **바이트 수**다(한글이 있어 617,744바이트 = 613,143자). 바이트와 문자를 맞대면 멀쩡한 번들도 「다르다」로 보인다 — 같은 단위로 비교해야 한다. / 해결: unregister + `caches.delete` 후 측정 경로의 **모든 내비게이션**에 서비스워커 차단 `initScript`를 붙이고 `ignoreCache: true`로 다시 쟀다. `reading` 샘플이 인라인 부트 실행 전(26·41ms) 2건뿐이고 그 뒤로는 끝까지 `study` — 수정이 실제로 먹은 것이 확인됐다. / **2회차(같은 날, #1151 실측)**: 같은 함정이 **더 고약한 얼굴**로 또 났다. 스킵 링크 CSS가 안 먹은 것처럼 보여(`position: static`) 확인해 보니 이번에도 옛 `app.css`(200,314자, 레포는 200,940자)였는데, **진단이 먼저 막혔다** — 차단용 `initScript`가 `navigator.serviceWorker`를 가짜 객체로 **덮어쓰기** 때문에 `controller`는 `null`, `getRegistrations()`는 `[]`를 돌려준다. 즉 **내가 심은 가짜를 내가 읽고 「서비스워커 없음」으로 판정**했다. 게다가 등록 차단은 **이미 활성인 SW가 fetch를 가로채는 것을 막지 못한다**(`cache: 'no-store'`도 SW 앞에서는 무력하다 — SW가 응답을 만들면 그만이다). 감별은 API가 아니라 **서버와 브라우저를 따로 읽어** 났다: `curl`이 준 `app.css`에는 규칙이 2건 있는데 페이지가 받은 것에는 0건 — 그래서 「서버는 맞고 브라우저가 틀리다」가 확정됐다. 처방: 차단 스크립트 **없이** 한 번 들어가 진짜 `navigator.serviceWorker.getRegistrations()`로 unregister + `caches.delete`를 하고, 그다음 이동부터 차단을 건다. / 재발방지: ① 측정 세션의 서비스워커 차단은 첫 이동이 아니라 **매 이동**에 건다. ② 「고쳤는데 그대로다」가 나오면 앱을 의심하기 전에 **지금 브라우저가 받은 자산이 저장소 파일과 같은지**부터 같은 단위로 대조한다. ③ **관측을 위해 심은 스텁은 그 관측의 눈도 가린다** — 무언가를 덮어썼으면 그 API로는 상태를 판정하지 않는다. 판정은 스텁이 못 건드리는 경로(`curl` 대 브라우저, 렌더된 값)로 한다. ④ 등록 차단 ≠ 제어 해제. 이미 등록된 SW는 unregister + 새 문서 로드까지 해야 손을 뗀다. / **뿌리 확정(2026-09-17 실측) — 로컬 검증 서버에서만 나는 함정이고 운영엔 없다**: `sw.js`는 정적 자산을 **cache-first**로 주는데, 그게 안전한 근거는 「Spring resource chain이 내용 해시 URL을 만든다 — 내용이 바뀌면 URL이 달라져 stale 불가」(`sw.js` 2~3행 주석)다. 같은 코드에서 페이지가 참조하는 URL을 `curl`로 대조했다: **운영 `booktimer.app/login`은 `/css/app-8e04dbc4….css`·`/pwa-install-5c127e0a….js`(해시)**, **로컬 `bootTestRun`(H2 파일 DB, `build/run-local-h2.cmd`)은 `/css/app.css`·`/pwa-install.js`(해시 없음)**. 해시가 없으니 cache-first가 파일 내용이 바뀌어도 같은 URL로 옛 캐시를 계속 준다 — 두 회차가 전부 이것이다. 해시가 꺼진 기제는 **추정**이다: `spring.web.resources.chain.strategy.content.*`는 `src/main/resources/application.properties`(93~94행)에만 있고 `src/test/resources/application.properties`엔 없는데, `bootTestRun`은 테스트 클래스패스라 같은 이름의 테스트 설정 파일이 main 것을 가린다(확인한 것은 「로컬 URL에 해시가 없다」까지, 가림 자체는 미확인). ⑤ **하드픽스(머신 로컬, 2026-09-17 적용·실측)**: 로컬 검증 서버에서도 콘텐츠 해시를 켰다 — `build/run-local-h2.cmd`에 환경변수 `SPRING_WEB_RESOURCES_CHAIN_STRATEGY_CONTENT_ENABLED=true`·`SPRING_WEB_RESOURCES_CHAIN_STRATEGY_CONTENT_PATHS=/**` 두 줄. 테스트 설정 파일은 건드리지 않았다(MockMvc 단언이 해시 없는 경로를 볼 수 있다). 적용 뒤 로컬 `/login`이 `/css/app-352a6b53….css`·`/pwa-install-5c127e0a….js`를 참조했고(후자와 `theme-ada058bd….js`는 **운영과 같은 해시** — 같은 내용이면 같은 URL이라는 교차 확인), 해시 CSS는 HTTP 200·**245,041바이트 = 레포 파일 바이트 수**였다. 이제 cache-first가 로컬에서도 stale 불가라 ①~④의 의식이 **이 스크립트로 띄운 서버에서는** 필요 없다. ⚠️ 그 파일은 gitignore된 머신·워크트리 로컬이라 **새 PC·새 워크트리엔 없다** — 다시 만들 때 이 두 줄을 넣는다(메모리 `local-browser-login-by-user`에 절차가 있다). `./gradlew bootRun`(MySQL)은 메인 설정만 읽으니 원래 해시가 켜져 있을 것이다(미실측). / **관련**: T-071·T-075·T-080(SW stale 캐시 군 — 그 셋은 배포 후 서빙, 이 항목은 **실측 세션의 관측 경로**) · 글로벌 `browser-verify` 스킬 「관측 경로를 먼저 의심한다」
