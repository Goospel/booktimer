# T-160 · WebKit은 스크롤 컨테이너의 끝쪽 padding을 스크롤 영역에서 뺀다 — 가운데 정렬 캐러셀이 아이템이 적을수록 안 밀린다(2권 0px / 4권 절반)

증상: 홈 표지 캐러셀에서 **읽는 중 책이 2권이면** 옆 표지를 탭해도 가운데로 오지 않고 손가락으로도 안 밀렸는데, **4권으로 늘리자 정상 동작**했다. 데스크톱 크롬에서는 2권에서도 `scrollWidth 402 > clientWidth 302`로 여지가 100px 멀쩡히 잡혀 재현되지 않는다. / 원인: 첫·마지막 표지를 가운데까지 올리려고 트랙에 `padding: 0 calc(50% - 표지폭/2)`를 줬는데, **WebKit(iOS 웹뷰)은 스크롤 컨테이너의 끝쪽(end) padding을 scrollable overflow에 포함하지 않는다**(Blink는 포함 — 그래서 크롬 검증을 통과했다). 폭 W 화면에서 n권일 때 실제 밀 여지는 `(W/2 - 42) + (100n - 16) - W`가 되어, W=390이면 n=2에서 **-53 → 0**(전혀 안 움직임), n=4에서 147(정상값 300의 절반 — 마지막 두 권은 가운데까지 못 온다). 「아이템이 적으면 아예 안 되고 많으면 되는 것처럼 보인다」가 이 함정의 서명이다. / 해결: 가운데 정렬 여백을 **첫·마지막 아이템의 `margin`**으로 옮긴다 — flex 아이템의 마진 박스는 어느 엔진에서나 스크롤 영역에 들어간다. 값이 같으므로 i번째가 가운데 오는 위치 `i * (아이템폭 + 간격)`도 그대로라 계산 코드는 손대지 않는다. 세로 padding은 스크롤 축이 아니라 무관. / 재발방지: ① **가로 스크롤 컨테이너의 좌우 여백은 padding이 아니라 양끝 아이템 margin(또는 spacer)** — 스크롤 영역에 포함되는지가 엔진마다 갈리는 유일한 자리다 ② 렌더 단언으로 트랙 padding이 세로만인지 + 양끝 margin이 **정확히 1개씩**인지 못 박았다(모든 아이템에 붙으면 간격이 화면 폭만큼 벌어진다 — 돌연변이로 실측) ③ **Blink에서만 검증한 스크롤 geometry는 WebKit 보증이 아니다**: 크롬에서 `scrollWidth - clientWidth`가 기대값이어도 실기기에서 0일 수 있으니, 스크롤 여지가 걸린 변경은 **아이템 최소 개수(2개)에서 실기기 확인**을 게이트로 둔다. 1회차 신규 — 직전 T-159와 같은 캐러셀·같은 배포에서 나왔지만 메커니즘이 별개다(저쪽은 overflow-y가 터치 입력을 죽임, 이쪽은 end padding이 스크롤 영역에서 빠짐). 다만 **둘 다 「Blink에서 통과한 스크롤 CSS가 WebKit에서 다르게 계산된다」**는 한 뿌리라, 이 계열이 3회째가 되면 군으로 묶어 승격한다. 캐러셀 수정 배포 후 실기기 재확인에서 발견
