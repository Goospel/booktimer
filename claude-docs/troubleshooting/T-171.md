# T-171 · 새 불변식을 「그 값을 만드는 경로 한 곳」에만 걸면 조용히 거짓이 된다 — 예약이 안 걸린 가입 경로로 계정 탈취까지 갔다

증상: 「놓아준 옛 핸들은 영구 예약된다」는 불변식을 설계에 선언하고 구현했다. 전체 테스트 1635건 그린, 돌연변이 검증까지 통과. 그런데 **놓아준 핸들로 제3자가 그냥 신규 가입이 됐다** — 기능의 존재 이유가 통째로 거짓인 채 전 신호가 초록이었다. / 원인: 예약 검사(`existsByPreviousLoginId`)를 **아이디 변경 경로 한 곳에만** 넣었다. login_id를 정하는 경로는 넷(가입 · 온보딩 완료 · 미니앱 핸들 생성 · 변경)인데 나머지 셋은 옛 `existsByLoginId` 그대로였다. **DB도 못 막는다** — `login_id` UNIQUE는 값을 옮기는 순간 옛 자리를 비워 주므로 그 핸들은 «비어 있는» 상태가 된다. 테스트도 같은 사각을 공유했다(변경 경로만 단언). 그 결과 아이디를 바꾼 사용자의 열려 있던 세션(principal = 옛 핸들)이 브리지 폴백에서 **가입해 간 남의 계정**으로 해석돼 그 계정에서 전권으로 돌았다(소셜 탈퇴 확인 수단이 `confirmHandle == login_id`라 계정 삭제까지 도달). / 해결: 호출처마다 가드를 흩뿌리는 대신 판정을 `UserRepository.isLoginIdTaken()` **한 곳으로 모으고** 네 경로를 전부 그리로 보냈다 — 다음에 login_id를 정하는 경로가 생겨도 예약이 자동으로 지켜진다. 회귀 가드는 경로별 실 빈 통합 테스트(`LoginIdReservationIntegrationTest`, `@SpringBootTest`); 돌연변이(OR 절 제거)로 3건이 정확히 깨지는 것 확인. / 재발방지: ① 불변식을 새로 만들면 **그 값을 쓰는 모든 경로를 먼저 grep**하고, 가드는 **공유 함수 한 곳**에 둔다(루트 원인 수정 = 최소 diff이기도 하다). ② **「DB UNIQUE가 최종 방어선」은 그 컬럼에 값이 남아 있을 때만 참이다** — 값을 A에서 B로 «옮기는» 기능은 원래 자리의 UNIQUE 보호를 스스로 없앤다. 이동형 기능을 만들 땐 «옮긴 뒤 빈자리»를 누가 지키는지 명시한다. ③ 설계가 «영구 예약»이라 선언했다고 구현이 그런 게 아니다 — 리뷰는 선언을 읽지 말고 **그 불변식을 깨뜨리는 경로를 직접 태워봐야** 한다(이번엔 독립 리뷰가 실측 프로브로 잡았다. 설계·구현·테스트 셋이 같은 사각을 공유했기 때문에 그 안에서는 영영 안 보였다). 1회차 신규
