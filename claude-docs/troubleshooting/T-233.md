# T-233 · React 중복 key는 경고로 끝나지 않는다 — 형제 목록을 통째로 갈아끼울 때 중복 key의 첫 노드가 고아 DOM으로 남아, 다른 탭에 남의 행이 하나씩 쌓인다**) / **1회차

증상: 미니앱 홈 피드에서 「책 뉴스」 탭을 보고 「소식」·「함께 읽는 사람」으로 옮기면 뉴스 글 하나가 그 탭에 같이 남고, 탭을 왕복할수록 누적됐다(사용자 보고). 처음엔 **공부 모드에서만** 보이는 것처럼 관측됐지만, 조건은 모드가 아니라 **「중복 link 기사가 그려진 채 뉴스 탭을 떠났는가」**다 — 모드 전환은 `HomeFeedBox`를 재마운트하지 않아 이미 생긴 고아가 그대로 따라온다(그래서 「공부 모드 버그」로 좁혀 뒤졌다면 영영 못 찾았다). / 원인: 두 층이 겹쳤다. ① 서버 `HomeFeedApiController.newsFor`가 `book_news` 행을 그대로 내려보내는데 그 테이블의 유니크는 **`(isbn13, link)`**라, 같은 기사가 내 완독 책 두 권에 매칭되면 **같은 link가 두 줄** 내려온다. ② 미니앱이 그 link를 목록 key로 쓰고(`key={item.link}`), React 18은 형제 목록을 통째로 갈아끼울 때 중복 key의 **첫 노드를 삭제 목록에서 놓쳐** DOM에 고아로 남긴다(React 18 독립 재현: 뉴스→소식 전환 후 고아 `<a>` 1개, 재왕복 시 2개로 누적). 중복 key는 콘솔 경고로 끝나는 사소한 규칙 위반으로 읽히기 쉬운데, **실제로는 화면에 남는 결함**이다. / 해결: 뿌리인 서버에서 걷었다 — `newsFor`가 link 기준으로 중복을 제거하고, 스캔이 발행 최신순이라 **먼저 만난(가장 최신) 행**이 남는다(`bookTitle` 라벨도 그 행에서 온다). 상한(`MAX_NEWS`)을 자른 뒤 걷어 건수가 줄 수 있으나, 상한 전에 걷으려면 isbn별 그룹이 필요해(JPQL에 윈도 함수 없음) 과하다. 프론트 key는 손대지 않았다 — 서버가 걷으면 도달 불가한 경로다. / 재발방지: ① **목록 key는 서버가 유일성을 보장하는 값만 쓴다** — 유니크 제약이 복합키면 그 일부(여기선 `link`)만으로는 유일하지 않다는 것을 의심한다. ② **「다른 탭에 남의 행이 남는다」는 증상은 key 중복부터 본다** — 렌더 조건·상태 초기화를 뒤지기 전에. ③ 조인·1:N이 낳는 중복은 **표시 단위로 서버에서 걷어** 내려보낸다(화면마다 걷으면 화면 수만큼 늙는다). / **관련**: 「이상값을 만나면 관측 경로를 먼저 의심한다」의 사촌 — 여기선 관측이 아니라 **증상이 붙어 나타난 화면(공부 모드)**이 범인처럼 보였다.
