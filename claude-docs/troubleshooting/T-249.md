# T-249 · `git add`와 `git commit`을 한 명령으로 붙이면 번들 게이트가 「Bundle is stale」로 오판 차단한다 — PreToolUse는 add 이전 상태만 본다

**1회차** / 증상: 프론트 번들을 11섬 전수 재빌드해 `study`·`dashboard` 둘이 갱신된 것을 확인하고 그 산출물까지 add 대상에 넣었는데, `git add <파일들> && git commit -F .commit-msg-tmp`가 **`[BLOCKED] Bundle is stale: frontend source changed but built artifacts are not up-to-date`**로 막혔다(2026-09-16, PR #1146). 메시지가 지시하는 대로 빌드를 다시 돌려도 같은 자리에서 또 막힌다 — 빌드는 이미 최신이므로 영영 풀리지 않는다. / 원인: `require-bundle-build.ps1`은 **PreToolUse** 훅이라 명령이 실행되기 **전에** 돈다. 한 명령에 `&&`로 붙인 `git add`는 아직 실행되지 않았으니 **인덱스가 비어 있다**. 훅은 재빌드한 뒤 `git diff --exit-code -- src/main/resources/static`(인덱스 ↔ 워킹트리)으로 판정하므로, 갱신된 번들이 전부 「미스테이징 변경」으로 보여 stale이 된다. 훅의 `$selfStages` 로직이 「명령이 스스로 add하는가」를 보긴 하지만 그건 게이트 **발동 여부**를 정할 때만 쓰이고 최종 diff 판정에는 반영되지 않는다 — 「필요 없을 때 돌 수는 있어도 놓치지는 않는다」는 fail-safe 설계라, 이 오탐은 설계대로 동작한 결과다. / 해결: **`git add`를 별도 명령으로 먼저 실행하고 `git commit`만 따로 호출한다.** 인덱스에 번들이 들어 있으면 diff가 0이라 그대로 통과한다(실제로 분리 한 번에 풀렸다). / 재발방지: ① `frontend/**`가 걸린 커밋은 **add와 commit을 한 명령에 붙이지 않는다** — `&&`로 이어도 PreToolUse에는 add 이전 상태만 보인다. ② 「Bundle is stale」을 만나면 빌드를 다시 돌리기 **전에** `git status --short`로 `src/main/resources/static`이 스테이징돼 있는지 본다 — 앞칸이 `M `(스테이징)이면 빌드 문제가 아니라 **명령 구조 문제**다. ③ 훅 메시지가 처방(`git add` 후 재커밋)은 맞게 주지만 **진짜 원인을 가리지 않는** 사례다. 메시지를 「빌드가 낡았다」로 읽으면 빌드 루프에 빠진다. / **관련**: T-063(번들 재빌드 누락 — 이 게이트가 선 이유) · T-248·T-242·T-228(같은 훅군에서 **PreToolUse 시점의 상태**가 훅의 관점을 좁히거나 넓히는 문제군. T-242·T-228은 조용히 통과하는 방향, 이것과 T-248은 멀쩡한 명령을 막는 방향).
