# SNS 기능 — 설계 문서 (구현 전 합의용)

> **상태**: 설계 초안 (⏳ 2026-06-04). 코드 없음. 이 문서로 공유 모델·프라이버시·관계·스키마를 먼저 못 박은 뒤 TDD로 들어간다.
> **왜 설계 먼저**: SNS는 **데이터 노출·권한 경계가 핵심**이라, 설계 없이 시작하면 되돌리기 어려운 결정(공개 범위·스키마)이 코드에 굳는다.
> 비공개 기록이 한 번 새면 회수 불가 — 인가 경계는 사후 패치가 아니라 **설계 단계의 1순위**다.

## 1. 목표 / 비목표

### 목표
- 사용자가 **다른 사용자의 독서 활동**(어떤 책을 읽었나/읽는 중인가/책별 누적 시간/잔디)을 볼 수 있다.
- "함께 읽는 사람"이라는 **동기부여 축**을 만든다(혼자 읽기 → 사회적 독서).
- 책별 기록(완료된 핵심 콘텐츠)을 공유 단위로 활용한다.

### 비목표 (적어도 1차에선)
- 실시간 채팅·DM
- 댓글·좋아요 같은 풀 SNS 상호작용(후순위 — 먼저 "보기"부터)
- 알고리즘 추천 피드(초기엔 단순 시간순/팔로잉)
- 공개 글쓰기(독후감 등) — 별도 기능, SNS와 분리

## 2. 핵심 통찰 — "남에게 보여주려면 DB에 저장해야 하나?" → 아니다 (N-037)

독서 데이터는 **이미 전부 저장돼 있다**:
- "누가 어떤 책을 읽었나/읽는 중인가" → `book`(`user_id` 소유, `status`, `isbn13` 식별)
- "얼마나 읽었나" → `reading_session`(`book_id` + `duration_seconds`)

SNS에서 남의 걸 보여주는 건 **데이터 추가가 아니라 조회 주체를 바꾸는 것**이다:
```
기존:  where user_id = 나
SNS:   where user_id = 그 사람   (단, 그 사람이 공개했고 / 내가 볼 권한이 있을 때만)
```

따라서 SNS가 **새로 저장해야 하는 건 독서기록이 아니라 두 가지뿐**:
1. **관계** — 누가 누구를 팔로우/친구하는가
2. **공개 범위** — 각 사용자가 자기 기록을 누구에게까지 보이는가

그리고 `where user_id`를 갈아끼우는 **그 순간 IDOR/공개범위 체크가 보안 경계**가 된다(비공개 기록 누출 방지). 이게 이 기능의 가장 위험한 지점.

## 3. 공개 범위 / 프라이버시 모델

### 3.1 공개 범위 enum (제안)

```
enum Visibility {
    PRIVATE,    // 나만 (기본값)
    FOLLOWERS,  // 나를 팔로우하는 사람까지
    PUBLIC      // 누구나(비로그인 포함 — SEO 공개 프로필)
}
```

### 3.2 기본값 = **PRIVATE (opt-in 공개)**

- **왜 비공개 기본**: 기존 사용자는 "내 독서는 나만 본다"를 전제로 가입했다. 마이그레이션으로 갑자기 공개되면 **프라이버시 사고**다.
  새 컬럼 `visibility`를 추가할 때 **기존 행은 전부 PRIVATE로 백필**, 공개는 사용자가 명시적으로 켠다.
- 온보딩/설정에서 "내 독서 활동을 공개할까요?" 토글 제공.

### 3.3 공개 단위 — 1차는 프로필 단위 토글 하나

세분화(책 목록은 공개·시간은 비공개 등)는 매력적이지만 **UI·권한 분기 폭증**. 1차엔:
- **프로필 전체에 단일 `visibility`** 하나만. 켜면 (책 목록 + 책별 시간 + 잔디) 묶음이 같이 공개.
- 세분화(항목별 공개)는 수요 확인 후 **후속 컬럼**으로 확장(스키마가 이를 막지 않게 enum/별도 테이블 여지만 남김).

### 3.4 노출 항목 화이트리스트 (공개돼도 절대 안 나가는 것)

공개 프로필이라도 **다음은 절대 노출 금지** — 응답 DTO에 아예 담지 않는다(필드 누락이 아니라 설계적 차단):
- 이메일, `password_hash`, provider 식별자, 로그인 IP/세션
- 타이머 내부값(remaining/cap 등 부채 상태 — 동기부여와 무관, 사생활)
- 정확한 타임스탬프(언제 몇 시에 읽었는지) → **날짜 단위로만**(잔디는 일자 농도라 이미 안전)

노출 허용 화이트리스트(공개 시):
- 닉네임, (선택)자기소개, 책 목록(제목·표지·상태), 책별 누적 시간(분 단위), 잔디(일자 농도), 총 독서 시간

## 4. 관계 모델

### 4.1 팔로우(단방향) vs 친구(양방향)

| | 팔로우(단방향) | 친구(양방향) |
|---|---|---|
| 승인 | 불필요(바로 팔로우) | 요청→수락 필요 |
| 데이터 | `(follower, followee)` 1행 | 보통 요청 상태 머신 + 양쪽 표현 |
| 복잡도 | 낮음 | 높음(pending/accepted/blocked 상태) |
| 사례 | 트위터·인스타 | 페이스북·카톡 |

### 4.2 결정(제안): **팔로우(단방향)부터**

- 독서 공유는 "관심 있는 사람을 구독"에 가깝지 "상호 승인"이 본질이 아님 → 팔로우가 자연스럽고 가볍다.
- 승인 상태 머신이 없어 **스키마·로직이 단순**(1차에 적합).
- 비공개 계정은 `visibility=PRIVATE/FOLLOWERS`로 처리 — "팔로우는 누구나 가능하되, 보이는 건 공개범위가 결정". (인스타식: 비공개 계정은 팔로우 *요청*이 필요 → 이건 후속에서 FOLLOWERS+승인으로 확장 가능)

### 4.3 1차 단순화

- **팔로우 = 즉시 성립**(승인 없음). 비공개 보호는 `visibility`가 담당.
- "팔로우 요청·수락"(비공개 계정 승인제)은 **후속** — 필요해지면 `follow`에 `status` 컬럼(PENDING/ACCEPTED) 추가로 확장.

## 5. 권한 경계 (IDOR) — 가장 위험한 지점

### 5.1 모든 "남의 데이터 조회"는 가시성 게이트를 통과해야 한다

`viewer`(보는 사람)가 `target`(대상)의 독서 데이터를 볼 수 있는가:

```
canView(viewer, target):
    if viewer == target:              return true        # 내 것
    switch target.visibility:
        PUBLIC:    return true
        FOLLOWERS: return isFollowing(viewer, target)     # viewer가 target을 팔로우?
        PRIVATE:   return false
```

- 이 체크를 **모든 SNS 조회 진입점에서 강제**(컨트롤러 진입 즉시). 빼먹으면 곧 IDOR.
- 비로그인 viewer는 PUBLIC만 통과.
- **차단(block) 관계가 생기면** canView 맨 앞에 `if isBlocked(target, viewer) return false` 추가.

### 5.2 열거(enumeration) 완화

- 공개 프로필 URL이 `/u/{id}` 순번이면 **전수 크롤링** 쉬움 → 닉네임 기반 `/u/{handle}` 또는 불투명 식별자 고려.
- 프로필 검색·목록은 **PUBLIC만** 노출. PRIVATE/FOLLOWERS 사용자는 검색 결과에서 제외.

### 5.3 테스트로 못 박을 보안 케이스 (TDD)
- viewer=target(본인) → 항상 보임
- PUBLIC → 비로그인도 보임
- FOLLOWERS → 팔로워는 보이고, 비팔로워·비로그인은 차단(403/404)
- PRIVATE → 본인 외 전원 차단
- 차단된 사용자 → 공개여도 차단
- DTO에 이메일/해시/타이머 내부값이 **절대 안 실림**(직렬화 누출 테스트)

> ⚠️ 권한 실패는 **404로 응답**(403 대신) 검토 — "그 사용자 있는데 못 본다"(403)는 존재를 누설. 비공개는 "없는 것처럼"(404)이 열거 방어에 유리.

## 6. 스키마 / 마이그레이션

### 6.1 새 테이블 — `follow` (관계)

```sql
-- V7__follow.sql (예시 — 구현 시 H2/MySQL 공통 문법 확인)
create table follow (
    id          bigint       not null auto_increment,
    follower_id bigint       not null,   -- 팔로우하는 사람
    followee_id bigint       not null,   -- 팔로우당하는 사람
    created_at  datetime(6)  not null,
    primary key (id),
    constraint uq_follow unique (follower_id, followee_id),   -- 중복 팔로우 방지
    constraint fk_follow_follower foreign key (follower_id) references users(id),
    constraint fk_follow_followee foreign key (followee_id) references users(id)
);
create index idx_follow_followee on follow (followee_id);  -- "나를 팔로우하는 사람" 조회
create index idx_follow_follower on follow (follower_id);  -- "내가 팔로우하는 사람" 조회
```

- `unique(follower_id, followee_id)` — 같은 사람 중복 팔로우 차단(앱 레벨 + DB 제약 이중).
- 자기 자신 팔로우(`follower==followee`) 금지 — 도메인 검증(`Follow.create`)에서 막고, 테스트로 고정.
- 인덱스 둘 다 필요: "팔로워 목록"(followee로 조회)·"팔로잉 목록"(follower로 조회) 양방향.

### 6.2 `users` 공개범위 컬럼 — `V8__user_visibility.sql`

```sql
alter table users add column visibility varchar(20) not null default 'PRIVATE';
-- 기존 행은 default 'PRIVATE'로 채워짐 — 갑작스런 공개 사고 방지(opt-in)
```

- enum은 varchar로 저장(N-023/Flyway baseline 관례 — MySQL·H2 공통). 길이 20.
- `not null default 'PRIVATE'` — 기존 사용자 백필이 곧 "비공개 유지".

### 6.3 (후속, 1차 제외) 차단 — `block`

```sql
-- 후속: 악용 대응 단계에서
create table block (
    id          bigint not null auto_increment,
    blocker_id  bigint not null,
    blocked_id  bigint not null,
    created_at  datetime(6) not null,
    primary key (id),
    constraint uq_block unique (blocker_id, blocked_id)
);
```

### 6.4 안 건드리는 것
- `book`, `reading_session` — **변경 없음**(N-037). 조회 `where user_id`만 바뀐다.
- 책 인기 카운트(§7.1)는 `book`을 `isbn13`로 `group by`만 — 테이블 추가도 없음.

### 6.5 Flyway 번호 조율
- 현재 마지막 **V6**(`V6__user_onboarded.sql`). SNS는 **V7부터**.
- ⚠️ 다중 세션 동시 작업 시 번호 충돌 주의([CLAUDE.md](../CLAUDE.md) 워크트리 규칙) — 머지 직전 번호 부여 권장.

## 7. 단계별 구현 로드맵 (incremental — big-bang 아님)

> 각 단계가 **독립 출시 가능**하도록 쪼갠다. 뒤로 갈수록 권한 경계가 무거워진다.

### 7.1 1단계 — 책 인기 카운트 (관계 0, 가장 가벼움) ✅ 선출시 후보
- **이미 plan.md에 상세 설계됨**(§SNS 책 인기 카운트). 새 테이블·관계 **불필요**.
- 검색 결과·내 책장에 "읽는 중 N · 완독 M" — `isbn13` distinct user count.
- 프라이버시 = **집계(기수)만 노출** → 개인 식별 없음 → 공개범위 설계 부담 작음.
- ⚠️ **소수 재식별**(1~2명이면 특정 가능) → k-익명성 최소 임계값(예: N≥3에서만 노출) 검토.
- ⚠️ N+1 회피 — 페이지당 ISBN 한 번의 `group by`로 일괄 집계.
- **이 단계는 SNS 설계(관계·공개범위)와 거의 독립** → 가장 먼저 손대기 좋음.

### 7.2 2단계 — 공개범위 컬럼 + 공개 프로필 페이지 (관계 0)
- `users.visibility` 추가(V8), 설정에 공개 토글.
- `GET /u/{handle}` 공개 프로필 — PUBLIC인 사용자의 책 목록·책별 시간·잔디.
- 관계 없이도 PUBLIC↔PRIVATE만으로 동작. **SSR로**(SEO).
- canView는 아직 `PUBLIC or self`만(FOLLOWERS는 3단계에서).

### 7.3 3단계 — 팔로우 (관계 도입)
- `follow` 테이블(V7) + 팔로우/언팔로우 + 팔로워/팔로잉 목록.
- `visibility=FOLLOWERS` 활성화 → canView에 `isFollowing` 분기 추가.
- 팔로잉 피드(내가 팔로우한 사람들의 최근 독서) — 시간순.

### 7.4 4단계 — 악용/스팸 대응 (운영 안정화)
- 차단(block) 테이블, 신고, 열거 완화(handle 불투명화), 레이트리밋.
- 공개 프로필 크롤링 대응.

### 7.5 (선택) 5단계 — 상호작용
- 댓글·좋아요·"같이 읽기" 등. 풀 SNS. 수요 확인 후.

## 8. 화면별 SSR / SPA 판단 → 프론트 결정과 연결

> 이게 [plan.md §프론트엔드 전환]의 "두 번 짜기" 리스크를 **실측**하는 자리다. 화면마다 요구가 다르다.

| SNS 화면 | 렌더 | 이유 |
|---|---|---|
| 공개 프로필(`/u/{handle}`) | **SSR** | SEO·검색 노출·수익 축(N-017). 외부 비로그인 진입점 |
| 책 인기 카운트(검색·책장) | **SSR** | 기존 SSR 페이지에 숫자만 추가. 인터랙션 미미 |
| 팔로우/언팔로우 버튼 | SSR + htmx 또는 작은 JS | 단일 액션. 현재 스택(htmx/Alpine)으로 충분 가능 |
| 팔로잉 피드 | **판단 보류** | 무한 스크롤·실시간성 요구가 크면 SPA 후보. 초기엔 시간순 페이지네이션 SSR로 시작 |

**결론**: SNS 대부분이 **SSR로 충분/유리**(특히 SEO 필요한 공개 프로필). **"SNS = SPA 필요"라는 전제가 약하다** →
"SNS 두 번 짜기" 리스크는 **생각보다 작다**. 진짜 SPA 후보는 피드뿐이고, 그마저 페이지네이션 SSR로 출발 가능.
→ **API-first big-bang을 정당화하지 못함.** 피드가 실제로 인터랙션 헤비해지면 그때 그 화면만 incremental 전환.
